# 좌석 현황 캐시 전체 흐름

작성일: 2026-09-10

관련 패키지: [Seat Availability 패키지](README.md) · [전체 문제 해결 안내](../../portfolio/lock-to-waiting-room-reading-guide.md)

## 1. 문서 범위

이 문서는 Waiting Room에서 입장이 허용된 사용자가 좌석 현황을 조회한 뒤, Redis snapshot·MySQL projection·single-flight·무효화가 어떤 순서로 실행되는지 설명한다. Waiting Room의 join·승급·SSE·polling은 [Waiting Room 전체 흐름](../waiting-room/146.14-waiting-room-flow.md)에서 다룬다.

좌석 선점의 최종 상태는 MySQL이 결정한다. Redis는 좌석 화면에 제공할 조회 snapshot을 보관한다. 캐시는 `pre-reserve`의 성공 여부를 결정하지 않고, 반복되는 전체 좌석 조회가 MySQL과 HikariCP를 사용하는 횟수를 줄인다.

## 2. 요청이 캐시에 도달하는 조건

```text
Client
  → GET /api/seats/{performanceTimeId}
  → SeatController
  → WaitingRoomAccessGuard
       ├─ Waiting Room 미적용 회차: BYPASS
       └─ 적용 회차: entry pass·회원·회차·만료·ticket 상태 검증
  → SeatService.viewSeatMap()
  → SeatMapCacheReader.read()
```

`WaitingRoomAccessGuard`가 보호 구역 진입을 허용한 뒤에만 좌석 현황 조회가 실행된다. 대기열 미적용 회차에서는 `BYPASS`로 좌석 조회에 들어간다. 캐시 적용 여부는 [SeatMapCacheFeaturePolicy](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapCacheFeaturePolicy.java)가 전역 설정과 대상 회차 목록을 함께 확인해 결정한다.

## 3. 캐시 적중·누락 흐름

```text
SeatMapCacheReader.read(performanceTimeId)
  → 회차별 캐시 적용 여부 확인
  → single-flight 활성화 여부 확인
  → RedisSeatMapCacheStore.get()
       → version·versioned snapshot·legacy snapshot MGET
       ├─ 현재 version과 snapshot version 일치
       │    → 좌석 목록 반환
       └─ key 없음·version 불일치·snapshot 오류
            → 재구축 경로
```

1. [SeatController](../../../src/main/java/org/example/ticket/reservation/booking/controller/SeatController.java)가 entry pass를 검사한 뒤 [SeatService](../../../src/main/java/org/example/ticket/reservation/booking/service/SeatService.java)의 `viewSeatMap()`을 호출한다.
2. [SeatMapCacheReader](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapCacheReader.java)는 해당 회차가 캐시 대상인지 확인한다. 캐시가 비활성화된 회차는 [SeatMapDatabaseReader](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapDatabaseReader.java)를 통해 MySQL projection을 수행한다.
3. 캐시가 활성화되면 [RedisSeatMapCacheStore](../../../src/main/java/org/example/ticket/reservation/booking/cache/RedisSeatMapCacheStore.java)가 회차 version과 snapshot을 읽는다. 현재 version과 snapshot 안의 version이 같을 때만 적중으로 처리한다.
4. 적중한 snapshot은 좌석 현황 응답으로 변환된다. 응답 크기·JSON 직렬화·HTTP 전송은 요청마다 실행되므로, 캐시 적중은 MySQL projection 비용을 줄이는 효과로 측정한다.

## 4. 캐시 누락과 single-flight 재구축

```text
동일 회차의 동시 cache miss
  → 첫 요청: owner
       → in-flight future 등록
       → version V 읽기
       → MySQL 전체 좌석 projection 1회
       → version V 조건부 Redis 저장
       → future 완료
  → 나머지 요청: joiner
       → owner future 대기
       → 같은 좌석 목록 결과로 각자 HTTP 응답 생성
```

[SeatMapCacheReader](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapCacheReader.java)는 회차별 `CompletableFuture`를 `ConcurrentMap`에 저장한다. 먼저 등록된 요청이 owner가 되고, 이후 요청은 joiner가 되어 owner의 결과를 기다린다. 이 single-flight는 현재 JVM 범위에서 동작한다. 여러 애플리케이션 인스턴스가 각각 owner를 만들면 전역 단일 재구축이 보장되지 않는다.

owner는 Redis snapshot을 한 번 더 확인한 뒤 현재 version을 읽고 [SeatMapDatabaseReader](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapDatabaseReader.java)로 전체 좌석을 읽는다. 조회가 끝난 뒤 Redis version이 owner가 시작할 때 읽은 값과 같을 때만 snapshot을 저장한다. version이 달라지면 조건부 저장을 거부하고, 오래된 좌석 목록이 최신 상태를 덮어쓰지 않게 한다.

joiner는 설정된 대기 시간 안에 owner의 future를 기다린다. owner가 성공하면 각 joiner가 같은 좌석 목록으로 응답을 만들고, owner가 실패하거나 대기 시간이 초과되면 기존 오류 계약에 따라 종료한다. single-flight 결과 공유는 좌석 목록 재구축을 합치며, JSON 직렬화와 네트워크 전송은 요청별로 남는다.

## 5. Redis 장애와 데이터베이스 대체 조회

```text
Redis snapshot 조회 실패
  → 회차별 fallback Semaphore 획득
       ├─ 허용 수 안: MySQL 좌석 projection
       └─ 허용 수 초과: 503 Service Unavailable
```

Redis 장애 때 모든 요청을 MySQL로 보내면 캐시 장애가 데이터베이스 부하로 확산될 수 있다. [SeatMapCacheReader](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapCacheReader.java)는 회차별 대체 조회 허용량을 제한하고, 허용량을 초과한 요청에는 명시적인 `503 Service Unavailable`을 반환한다. 이 경계는 좌석 조회의 성공률보다 MySQL의 최대 유입량을 먼저 보호하기 위한 운영 계약이다.

## 6. 좌석 상태 변경과 snapshot 무효화

```text
좌석 상태 변경 transaction
  → SeatMapInvalidationPublisher
  → Spring transaction commit
  → AFTER_COMMIT listener
  → Redis Lua
       ├─ 회차 version INCR
       └─ versioned·legacy snapshot DEL
  → SeatMapCacheReader read gate 세대 교체
```

[SeatMapInvalidationPublisher](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapInvalidationPublisher.java)는 좌석 상태 변경 지점에서 회차별 무효화 이벤트를 발행한다. 실제 Redis 변경은 [SeatMapCacheInvalidationListener](../../../src/main/java/org/example/ticket/reservation/booking/cache/SeatMapCacheInvalidationListener.java)가 `AFTER_COMMIT` 단계에서 실행한다. 트랜잭션이 롤백되면 무효화 Listener가 실행되지 않으므로 변경되지 않은 snapshot을 불필요하게 삭제하지 않는다.

[RedisSeatMapCacheStore](../../../src/main/java/org/example/ticket/reservation/booking/cache/RedisSeatMapCacheStore.java)의 무효화 Lua는 version 증가와 snapshot 삭제를 함께 실행한다. 이후 조회는 새 version의 snapshot을 재구축한다. 무효화 실행이 실패해도 이미 커밋된 MySQL 예약 결과는 유지하고, snapshot TTL과 다음 MySQL projection이 stale 데이터를 복구하는 보조 수단이 된다.

## 7. 전체 흐름에서 확인할 상태

| 단계 | 권위 데이터 | Redis 역할 | 실패 시 경계 |
|---|---|---|---|
| entry pass 검증 | Waiting Room ticket·서명 pass | ticket 상태 조회 | 접근 거부 |
| 좌석 현황 적중 | MySQL 상태를 반영한 snapshot | versioned JSON snapshot 반환 | 응답 처리·전송 비용 관측 |
| 좌석 현황 누락 | MySQL Seat와 좌석 상태 변경 트랜잭션 | projection 결과 저장 | single-flight로 DB 재구축 합침 |
| `pre-reserve` | MySQL transaction·행 잠금 | 좌석 조회 결과 제공 | 캐시 결과로 확정하지 않음 |
| commit 이후 | MySQL 커밋 결과 | version 증가·snapshot 삭제 | 무효화 실패 metric·TTL 복구 |
| Redis 장애 | MySQL | fallback 동시성 예산 | 초과 요청 503 |

## 8. 측정 결과와 현재 판단

캐시의 효과는 서로 다른 조건으로 나눠서 판단한다.

| 조건 | 관측 결과 | 판단 |
|---|---|---|
| 웜 캐시 2,000건 | MySQL projection 2,000회 → 0회, HikariCP pending 166 → 0 | 반복 조회의 DB 진입 감소 |
| 통제 cold miss 300건 | projection 301회 → 1회, 300건 성공 | same-JVM single-flight 효과 |
| 쓰기 50/s + 조회 100/s | 조회 p95 7,261ms → 996ms, projection 1,701회 → 229회 | 혼합 부하 적용 가치 확인 |
| 무효화 직후 2,000건 | 캐시 활성 projection 4회, HTTP 성공 101건 | DB 보호와 HTTP 응답 용량을 별도 관리 |
| Redis 명령 격리 | 무효화 Lua p99 1.511ms, 조건부 305KB 저장 p99 95.487ms | full snapshot 저장·전송 비용 후속 측정 |
| AFTER_COMMIT 실패·프로세스 종료 | stale snapshot 관측 후 TTL·재조회로 복구 | 최신성 SLO와 내구성 이벤트 전달 검토 |

원문 결과는 [148.1 종합 결과](148.1-results-and-decision.md), [single-flight·version 결과](146.6.4-single-flight-versioned-snapshot-result.md), [캐시 스탬피드 원인 분해](146.6.3-seat-map-cache-churn-stampede-decision.md), [무효화 실패 재현](148.3-after-commit-cache-invalidation-failure-test.md)에서 확인한다.

## 9. 현재 구현과 후속 경계

현재 구현은 Redis snapshot, Cache-Aside, same-JVM single-flight, version 조건부 저장, `AFTER_COMMIT` 무효화, 회차별 DB fallback 상한을 포함한다. TTL은 snapshot의 보조 복구 수단이다.

TTL jitter, refresh-ahead, stale-while-revalidate, 다중 JVM 전역 single-flight, Transactional Outbox, Message Bus는 현재 구현에 포함하지 않았다. 이 기능들은 stale 최신성 목표, 다중 인스턴스 운영, 독립 소비자, 자동 재처리 요구를 측정한 뒤 별도 결정으로 다룬다.
