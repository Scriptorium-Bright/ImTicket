# Waiting Room 전체 흐름

작성일: 2026-08-26

기준일: 2026-08-24  
관련 문서: [ADR](146.12-waiting-room-admission-boundary-adr.md) · [의사결정 로그](146.13-waiting-room-decision-log.md) · [C 결과](../../test/2026-08-24-waiting-room-c-same-seat-contention.md) · [C 이후 완료 순서](146.15-waiting-room-post-contention-completion-order.md) · [A1·A2 비교](../../test/2026-08-20-waiting-room-a1-a2-comparison.md)

이 페이지는 사용자 요청이 대기열에 들어가고, 입장하고, 좌석을 선점하는 경계를 한 번에 보여준다.

## 1. 전체 구성

```text
┌────────┐       ┌──────────────┐       ┌────────────────────┐
│ Client │──────▶│ Nginx Gateway│──────▶│ Waiting Room Service│
└────────┘       └──────┬───────┘       └─────────┬──────────┘
                        │                          │
                        │ 그 외 예약 API            │ Redis ZSET·Hash·Lua
                        ▼                          ▼
                 ┌───────────────┐          ┌──────────────┐
                 │ Reservation   │          │ WAITING /    │
                 │ Application   │          │ ADMITTED     │
                 └──────┬────────┘          └──────┬───────┘
                        │                          │
                        │ seat map / pre-reserve   │ SSE·폴링·entry pass
                        ▼                          ▼
                 ┌───────────────┐◀───────────────┘
                 │ MySQL         │
                 │ Seat/Reservation│
                 └───────────────┘
```

Nginx는 Waiting Room 경로를 Waiting Room Service로 전달하고, 그 외 예약 경로를 Reservation Application으로 전달한다. Waiting Room Service는 입장 상태를 관리한다. Reservation Application은 entry pass를 확인한 뒤 좌석 기능을 제공한다.

### 1.1 Nginx 도입 전: Reservation Application 직통 흐름

Nginx와 별도 Waiting Room Service를 도입하기 전에는 대기열 등록 요청이 Reservation Application의 `/join`으로 직접 들어갔다. Waiting Room의 Redis 상태와 승급 로직은 이미 있었지만, join·status·SSE·좌석 조회·pre-reserve 요청이 같은 애플리케이션의 Tomcat 실행 자원을 공유했다.

```text
Client
  → Reservation Application Tomcat `/join`
  → Redis ZSET·Hash·Lua
  → promotion scheduler
  → ticket status·SSE
  → seat map·pre-reserve
  → MySQL transaction·seat lock
```

2,000건 `/join` 직통 부하에서 Reservation Application Tomcat busy 최대 200이 관측됐다. 대기열 순번 계산의 Redis 비용과 별개로, 대기열에 들어오기 전 HTTP 요청이 예약 애플리케이션의 worker를 점유한 것이 첫 번째 ingress 병목이었다. 이 단계에서는 Waiting Room이 대기 상태를 관리했지만 예약 애플리케이션의 실행 자원과 분리되지 않았다.

### 1.2 Nginx Gateway 도입 단계

첫 번째 경계 실험에서는 Nginx가 `/join` 전달률을 초당 100건으로 조절하고, 요청을 기존 Reservation Application으로 전달했다. 이 단계에서는 서비스 코드를 분리하지 않고 Gateway에서 origin 유입 시점만 제어했다.

```text
Client
  → Nginx `limit_req` 100 requests/s, burst 2,000
  → Reservation Application Tomcat `/join`
  → Redis Waiting Room
  → promotion·status·SSE·seat map·pre-reserve
```

Nginx 경유 실행에서 origin Tomcat busy는 57~75로 낮아졌고 계약 성공률은 유지됐다. Gateway가 연결을 보유하므로 client `/join` p95는 약 19초였다. origin 보호 지표와 사용자 응답 지연을 별도로 기록해야 하는 이유가 이 단계에서 확인됐다.

### 1.3 Nginx Gateway와 별도 Waiting Room Service의 최종 라우팅

Gateway 실험의 외부 진입점은 호스트 `10082`이며 Nginx 컨테이너의 `80` 포트로 연결된다. Nginx는 Docker 네트워크의 서비스 이름을 upstream 주소로 사용한다.

```text
localhost:10082
  → waiting-room-gateway:80
      ├─ /api/reservation/waiting-room/{performanceTimeId}/join
      │    → limit_req 100 requests/s, burst 2,000
      │    → waiting-room-service:10080
      ├─ /api/reservation/waiting-room/**
      │    → waiting-room-service:10080
      └─ 그 밖의 예약 API
           → app:10080
```

join 경로는 Nginx `limit_req`를 먼저 통과한다. 허용량을 넘은 요청은 Nginx에서 429로 종료되고 Waiting Room Service에 도달하지 않는다. status·cancel·SSE 경로는 Waiting Room Service로 전달되며 SSE에는 buffering을 끄고 긴 read timeout을 적용한다. `proxy_pass`에 별도 URI가 없으므로 원래 HTTP 경로가 유지된다.

`waiting-room-service`는 같은 Spring Boot 이미지를 `TICKET_APPLICATION_ROLE=waiting-room`으로 실행한 인스턴스다. 이 설정으로 Waiting Room 컨트롤러와 승급 스케줄러가 활성화된다. 컨테이너 내부 포트는 `10080`이고 호스트 `10083` 포트는 직접 점검용으로 바인딩된다. Nginx는 호스트 포트 대신 Docker 네트워크의 `waiting-room-service:10080`을 사용한다.

join 응답으로 ticket과 현재 상태를 받은 뒤 클라이언트가 status·SSE를 요청한다. `ADMITTED` 상태와 entry pass를 받은 클라이언트는 `/api/seats/**`, `/api/reservation/pre-reserve`를 다시 호출하며 이 요청은 `app:10080`으로 이동한다. Gateway가 Waiting Room 처리 결과를 예약 애플리케이션으로 내부 전달하는 단계는 없다.

라우팅 근거: [Nginx Gateway 설정](../../../infra/nginx/waiting-room-gateway.conf), [Docker Compose 서비스·포트](../../../docker-compose.yml), [Waiting Room HTTP 컨트롤러](../../../src/main/java/org/example/ticket/reservation/waitingroom/controller/WaitingRoomController.java), [Waiting Room SSE 컨트롤러](../../../src/main/java/org/example/ticket/reservation/waitingroom/controller/WaitingRoomSseController.java).

## 1.4 Redis가 맡는 책임

Waiting Room에서 Redis는 하나의 자료구조로 모든 일을 처리하지 않는다. ticket의 현재 상태를 보관하는 Hash, 순번·만료 시각을 빠르게 찾는 Sorted Set(ZSET), 중복 join과 admission quota를 관리하는 키, 상태 변경 알림을 전달하는 Pub/Sub를 함께 사용한다. 각 키는 같은 회차 hash tag를 공유하므로 Lua가 여러 키를 한 번에 원자적으로 변경할 수 있다.

| Redis 구성 | 저장 내용 | 사용하는 이유 |
|---|---|---|
| `sequence` String | 회차별 단조 증가 순번 | 동시 join에 유일한 FIFO 순번 발급 |
| `waiting` ZSET | member=ticket ID, score=순번 | 앞 순번 조회·현재 순번(rank) 조회 |
| `deadline` ZSET | member=ticket ID, score=대기 만료 시각 | 만료 시각이 지난 WAITING ticket 일괄 검색 |
| `active` ZSET | member=ticket ID, score=entry lease 만료 시각 | ADMITTED active session 수·lease 만료 검색 |
| `ticket:{ticketId}` Hash | 회원·회차·상태·순번·대기 deadline·entry lease | 한 ticket의 현재 상태와 응답 데이터 |
| `owner:{memberId}` String | 회원의 현재 ticket ID | 동일 회원·회차 중복 join을 기존 ticket으로 수렴 |
| `admission` Hash | admission window·window count | 여러 인스턴스가 주기당 입장 quota를 공유 |
| Pub/Sub channel | ticket lifecycle event | 연결을 보유한 Waiting Room 인스턴스로 SSE 이벤트 전달 |

상태의 기준은 ticket Hash다. ZSET은 Hash를 빠르게 찾기 위한 인덱스 역할을 한다. `WAITING` ticket은 `waiting`과 `deadline`에 들어가고, `ADMITTED` ticket은 `waiting`·`deadline`에서 제거된 뒤 `active`에 들어간다. 취소·완료·만료가 되면 관련 ZSET member와 owner mapping을 정리하고 terminal 상태 Hash를 보존 기간 동안 남긴다.

```text
join
  → sequence INCR
  → ticket Hash 생성
  → waiting ZSET + deadline ZSET 등록
  → owner String 저장

promotion
  → waiting 앞 순번 선택
  → active session·admission quota 확인
  → waiting·deadline 제거
  → active ZSET 등록
  → ticket Hash를 ADMITTED로 변경

cancel / complete / expire
  → waiting·active·deadline에서 member 제거
  → owner mapping 삭제
  → ticket Hash terminal 상태 보존
```

Redis는 입장 순서·ticket 생명주기·active session·입장 quota와 상태 전달을 담당한다. 좌석의 `AVAILABLE → LOCKED → RESERVED` 정합성과 예약·결제 상태의 최종 확정은 MySQL transaction과 행 잠금이 담당한다. Redis의 `ADMITTED` 상태와 entry pass는 좌석 API 접근을 허용하는 조건이며 좌석 선점 결과를 확정하는 데이터가 아니다.

키 생성 규칙은 [WaitingRoomKeyFactory](../../../src/main/java/org/example/ticket/reservation/waitingroom/repository/redis/WaitingRoomKeyFactory.java), 원자적 상태 전이는 [join Lua](../../../src/main/resources/redis/waiting-room/waiting_room_join.lua)·[promotion batch Lua](../../../src/main/resources/redis/waiting-room/waiting_room_promote_batch.lua)·[transition Lua](../../../src/main/resources/redis/waiting-room/waiting_room_transition.lua)에서 확인한다.

## 2. join: 대기열 등록

```text
Client
  │ POST /api/reservation/waiting-room/{performanceTimeId}/join
  ▼
Nginx Gateway
  ▼
Waiting Room Service
  ▼
waiting_room_join.lua
  ├─ owner 중복 확인
  ├─ queue capacity 확인
  ├─ sequence INCR
  ├─ ticket Hash 생성
  ├─ waiting ZSET 등록
  ├─ deadline ZSET 등록
  └─ owner mapping 저장
  ▼
ticket 조회 + 순번 조회
  ▼
WAITING 응답
```

join의 핵심 상태 변경은 Lua 실행 안에서 원자적으로 처리한다. A1·A2 비교에서 비동기 join 인계는 계약을 충족했으나 Waiting Room Service Tomcat busy를 낮추지 않았고 A2 수락 p95는 A1보다 29.4% 높았다. Redis Stream 작업자, 비동기 join 설정, join-request SSE는 `e2f4150`에서 제거했다.

## 3. promotion: 입장 전환

```text
WaitingRoomPromotionScheduler
  │ 주기별 실행
  ▼
Redis promotion Lua
  ├─ waiting deadline 만료 정리
  ├─ active lease 만료 정리
  ├─ maxActiveSessions 확인
  ├─ admitPerInterval quota 확인
  ├─ 앞 순번 ticket 선택
  └─ WAITING → ADMITTED + entry pass
  ▼
Ticket 상태 저장
  ├─ 단일 instance: 해당 ticket 연결에 push
  └─ 다중 instance: Redis Pub/Sub → 연결 소유 instance → push
```

입장 처리의 기준 지표는 scheduler 실행 시간, 실제 입장률, Redis 명령 수, queue wait다. scheduler가 대기 시간 SLO를 제한할 때 batch Lua 연결을 검토한다.

## 4. 상태 조회와 재연결

```text
ADMITTED 인지
  ├─ SSE `GET .../events` 연결 유지 → 상태 변경 push
  ├─ HTTP polling `GET .../tickets/{ticketId}` → 15초마다 현재 상태 재조회
  ├─ SSE 연결 실패 → 재연결, 세 번 실패할 때 HTTP polling
  ├─ 새로고침       → 동일 owner의 ticket/status HTTP polling
  └─ entry pass 만료 → 접근 거부 또는 재입장 정책
```

SSE는 연결별 pending queue와 bounded executor를 사용해 상태 변경을 전달한다. HTTP polling은 브라우저가 status API를 호출해 Redis의 현재 ticket 상태를 받는 주기 조회다. 현재 프런트엔드는 SSE 연결 중에도 15초마다 HTTP polling을 수행하며, 연결 오류가 세 번 누적된 경우에도 수행한다. polling 응답에는 WAITING의 순번과 ADMITTED의 entry pass가 포함된다. 이 경로는 Pub/Sub 전달 누락·브라우저 재연결 뒤 화면을 복구한다. 따라서 상태 전달 비용은 SSE 연결 수와 HTTP polling RPS, Redis 호출 수, 서버 자원으로 측정한다.

## 5. protected zone: 좌석 조회와 선점

```text
Client + JWT + entry pass
  │
  ├─ GET /api/seats/{performanceTimeId}
  │       ▼
  │   WaitingRoomAccessGuard
  │       ▼
  │   Seat map 응답
  │
  └─ POST /api/reservation/pre-reserve
          ▼
      WaitingRoomAccessGuard
          ▼
      idempotency claim
          ▼
      좌석 상태 AVAILABLE 확인
          ▼
      DB lock / 선택된 lock 전략
          ▼
      Seat = LOCKED
      Reservation = PENDING_PAYMENT
      ReservedSeat 저장
          ▼
      transaction commit
          ▼
      성공 응답 + Waiting Room active slot 반환
```

동일 좌석의 동시 요청은 다음 결과를 만든다.

```text
요청 A ── DB lock ── AVAILABLE 확인 ── hold 성공
요청 B ── 상태 재확인 ── 409 Conflict
```

성공 요청과 충돌 요청의 p95/p99를 분리한다. 성공은 정확히 한 건이어야 한다. 나머지 요청은 빠르게 충돌 결과를 받아야 한다.

최신 C 실행은 10명·100명 모두 성공 1건과 `409 Conflict` N-1건을 기록했다. 100명 구간 충돌 p95는 3,367.930ms, p99는 3,427.402ms였고 Hikari pending 최대는 42였다. 정합성과 프로젝트 종료 SLO 5초를 통과했다. 잠금·입장 제어 코드를 변경할 때 C를 다시 실행한다. 상세 결과는 [C 결과 문서](../../test/2026-08-24-waiting-room-c-same-seat-contention.md)에 남겼다.

## 6. 만료·완료·새로고침

```text
WAITING
  ├─ waiting deadline 만료 → EXPIRED
  ├─ 사용자 취소          → CANCELED
  └─ promotion            → ADMITTED

ADMITTED
  ├─ entry lease 만료     → EXPIRED
  ├─ pre-reserve 성공     → COMPLETED + active slot 반환
  ├─ SSE 재연결           → 현재 ticket 상태 재조회
  └─ 새로고침             → owner·ticket·entry pass 재검증
```

Waiting Room ticket 만료와 결제 대기 Reservation 만료는 서로 다른 lifecycle이다. Reservation 만료는 별도의 정리 작업에서 좌석을 `AVAILABLE`로 복구한다.

## 7. 향후 확장 흐름

메시지 버스는 좌석 선점 명령의 응답 경로에 배치하지 않는다. 예약 커밋 이후의 상태 전파에 배치한다.

```text
Reservation + Outbox commit
          ▼
      Message Bus
       ├─ Redis 좌석 조회 모델 갱신
       ├─ 좌석 상태 SSE
       ├─ 알림
       └─ 분석·감사
```

Outbox, 중복 이벤트 처리, 재시도, 순서 키, 최종 일관성은 조회 모델 workload가 측정된 뒤 별도 ADR로 결정한다.

## 8. 경계별 지표

| 경계 | 확인할 지표 | 성공 조건 |
|---|---|---|
| Gateway → Waiting Room | join p95/p99, 429, Waiting Room Tomcat | ingress 계약과 capacity 계약 유지 |
| Waiting Room → Redis | Lua 지연, Redis CPU, queue wait | 순번·중복·만료·입장 전환 정합성 |
| Waiting Room → Reservation | entry pass 오류, active slot | 허용된 사용자만 protected zone 접근 |
| Reservation → MySQL | pre-reserve 성공/409 p95, Hikari pending, lock wait | 성공 1건, 충돌 빠른 실패, deadlock 0 |
| 상태 전달 | SSE 인지 지연, polling RPS, 재연결 | 상태 변경 인지와 자원 비용의 균형 |

## 9. 실행 순서

```text
A1 동기 join 직통 기준선·A2 비교 완료
  ↓
A1 동기 join Gateway 경유 완료
  ↓
B 고유 좌석 처리 용량 완료
  ↓
C 동일 좌석 경합 정합성 완료
  ↓
비동기 join 인계·join-request SSE 제거 완료
  ↓
빌드·동기 핵심 E2E 재검증 완료
  ↓
운영 후보값으로 D Gateway 전체 흐름 3회
  ↓
Ticket SSE·새로고침·재연결 1회
  ↓
ADR·의사결정 로그 갱신
  ↓
92.x~147 성능 개선 종료
```

최종 SLI·SLO와 중단 규칙은 [성능 개선 요약과 종료 기준](../../portfolio/waiting-room-performance-improvement-summary.md)을 따른다.

## 10. 줄글로 읽는 전체 흐름

사용자가 특정 공연 회차의 예매를 시작하면 브라우저는 `join` 요청을 Nginx Gateway로 보낸다. Gateway는 대기열 관련 요청을 Waiting Room Service로 전달한다. 이 서비스는 예약 애플리케이션과 실행 자원이 분리돼 있으므로, 많은 사용자가 대기열에 등록하거나 상태를 확인해도 좌석 조회와 선점을 처리하는 Reservation Application의 Tomcat 스레드와 HikariCP 연결을 사용하지 않는다. Waiting Room Service는 인증된 회원 식별자와 회차를 기준으로 Redis Lua 스크립트를 실행한다. 스크립트는 같은 회원의 기존 ticket을 확인하고, 대기열 수용량을 확인한 뒤, 순번을 증가시키고 ticket Hash·대기 순번 ZSET·만료 시각 ZSET·회원별 ticket mapping을 하나의 원자적 상태 변경으로 기록한다. 브라우저는 `WAITING` ticket ID와 현재 순번을 받은 뒤 대기 화면으로 이동한다.

대기 화면은 두 가지 상태 전달 경로를 함께 사용한다. 먼저 브라우저는 Ticket SSE 연결을 열고, Waiting Room Service는 인증과 ticket 소유자를 확인한 뒤 현재 snapshot을 초기 이벤트로 보낸다. 이후 promotion, 취소, 만료, 완료로 ticket 상태가 바뀌면 서비스 내부의 lifecycle event가 발생한다. 연결을 보유한 인스턴스는 `SseEmitter`로 이벤트를 보낸다. 인스턴스가 여러 대인 환경에서는 Redis Pub/Sub가 상태 변경을 연결 소유 인스턴스로 전달한다. SSE는 상태 변경을 빠르게 화면에 반영하는 경로다. 동시에 브라우저는 SSE가 열려 있는 동안에도 15초마다 status API를 HTTP polling으로 호출한다. 이 호출은 Redis의 최신 ticket Hash와 대기 순번을 다시 읽고, 입장이 허용된 상태에서는 entry pass를 함께 돌려준다. Redis Pub/Sub는 구독이 끊긴 시점의 이벤트를 보관하지 않으므로, polling은 전달 누락과 브라우저 재연결 뒤 화면을 Redis의 권위 상태에 맞추는 역할을 한다. SSE 오류가 세 번 누적되거나 사용자가 새로고침한 경우에도 status API가 같은 복구 경로가 된다.

WaitingRoomPromotionScheduler는 정해진 주기마다 Redis의 대기열을 처리한다. 이 작업은 먼저 waiting deadline이 지난 ticket과 entry lease가 끝난 active ticket을 정리하고, 현재 active session 수를 확인한다. 남은 여유가 있을 때만 주기당 입장 허용량(`admitPerInterval`)만큼 대기 순번의 앞쪽 ticket을 선택한다. 선택된 ticket은 Lua 안에서 `WAITING`에서 `ADMITTED`로 전환되고 entry lease를 갖는다. 그 결과는 SSE로 즉시 전달될 수 있고, 다음 HTTP polling에서도 같은 `ADMITTED` 상태로 확인된다. 브라우저는 status 응답 또는 SSE 이벤트에서 받은 entry pass를 저장한 뒤 좌석 선택 화면으로 이동한다.

좌석 조회와 `pre-reserve` 요청은 Reservation Application으로 전달된다. 이 경로의 Waiting Room 접근 검사기는 entry pass의 서명·회원·회차·만료 시각을 확인하고 Redis ticket이 아직 `ADMITTED`인지 확인한다. 검증을 통과한 사용자만 보호 구역에 들어가 좌석 현황을 조회하거나 좌석을 선점할 수 있다. 좌석 선점은 MySQL transaction과 좌석 잠금으로 처리한다. 같은 좌석을 동시에 요청하면 한 요청만 예약 대기 상태를 만들고, 나머지는 현재 상태를 다시 확인한 뒤 `409 Conflict`를 받는다. `pre-reserve`가 성공하면 Waiting Room ticket은 `COMPLETED`로 전환되고 active slot이 반환된다. 그래서 다음 promotion 주기에서 다른 대기 사용자를 입장시킬 수 있다.

사용자가 대기 중 취소하면 ticket은 `CANCELED`로 전환된다. waiting deadline까지 입장하지 못한 ticket과 입장 뒤 entry lease가 끝난 ticket은 `EXPIRED`가 된다. 이 상태 전이도 SSE와 HTTP polling에서 확인할 수 있다. Waiting Room ticket의 만료는 좌석 선점 뒤 생성되는 Reservation의 만료와 별도로 관리한다. Reservation 만료는 이후 정리 작업이 좌석을 다시 `AVAILABLE`로 바꾼다. Waiting Room은 MySQL에서 동기적으로 결정하는 좌석 조회·선점 경로에 동시에 들어갈 사용자 수를 제한하고 상태를 안내하는 입장 제어 계층이다.
