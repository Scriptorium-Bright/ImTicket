# 단일 서버 메모리 Waiting Room 대안 의사결정

작성일: 2026-09-10  
상태: 현재 애플리케이션 경로에 적용하지 않음 · 테스트 전용 비교 구현 기록  
상위 문서: [Waiting Room 의사결정 로그](146.13-waiting-room-decision-log.md) · [Waiting Room 저장 방식 결정](146.16-waiting-room-queue-alternatives-decision.md)

## 1. 검토 질문

Waiting Room Service를 한 대의 서버에서만 실행한다면 Redis 없이 JVM 메모리 자료구조로 대기열을 운영할 수 있는지 검토했다. 이 기록은 애플리케이션 경로에 연결하는 변경을 뜻하지 않는다. 현재 Redis 구조와 비교할 수 있는 단일 서버 대안을 포트폴리오에 남기는 것이 목적이며, 비교 실행을 위해 `src/test` 아래에 별도 저장소를 둔다.

## 2. 결정

현재 ImTicket의 Waiting Room은 Redis ZSET·Hash·Lua 구조를 유지한다. 단일 서버에서 재시작 시 대기 상태 유실을 허용하고, 수평 확장·장애 전환·강한 재접속 연속성이 필요하지 않은 환경에서는 메모리 대기열이 유효한 선택지가 될 수 있다.

현재 요구사항에는 다음 계약이 포함되어 있어 메모리 대기열을 제품 경로로 채택하지 않았다.

- 여러 Waiting Room 인스턴스가 같은 순번과 ticket 상태를 조회한다.
- 배포·재시작 뒤에도 대기 ticket과 입장 상태를 복구한다.
- `waiting`, `deadline`, `active`, ticket, owner, admission 상태를 함께 전이한다.
- SSE 연결이 다른 인스턴스로 재연결되어도 같은 상태를 확인한다.
- join·승급·취소·완료의 여러 상태 변경을 하나의 원자적 전이로 처리한다.

메모리 구현은 단일 서버 프로토타입, 테스트 기준선, 상태 유실을 허용하는 임시 대기열의 후보로 기록한다.

## 3. 후보 자료구조와 현재 Redis의 대응

한 JVM 안에서 현재 계약을 흉내 내려면 FIFO queue 하나만으로는 부족하다. 순번, 상태, 만료, 소유자, 활성 세션을 각각 보관하고 여러 자료구조를 함께 변경해야 한다.

| 현재 Redis 역할 | 단일 서버 후보 | 필요한 이유 |
|---|---|---|
| `sequence` String | `AtomicLong` | 동시 join에 중복되지 않는 단조 증가 순번 발급 |
| `waiting` ZSET | `ConcurrentSkipListMap<Long, UUID>` | 순번 정렬, 앞 순번 조회, ticket 삭제 |
| `deadline` ZSET | `DelayQueue<ExpiryTask>` 또는 별도 정렬 map | 대기 만료 대상의 시간순 처리 |
| `active` ZSET | `DelayQueue<LeaseTask>` 또는 별도 정렬 map | 입장권 lease 만료와 활성 세션 계산 |
| ticket Hash | `ConcurrentHashMap<UUID, TicketState>` | 상태·회원·회차·순번·만료 시각의 기준 데이터 |
| owner mapping | `ConcurrentHashMap<OwnerKey, UUID>` | 동일 회원·회차의 중복 join을 기존 ticket으로 수렴 |
| admission Hash | 회차별 `AdmissionWindow` 객체 | 주기별 입장량과 활성 세션 상한 공유 |
| Lua 상태 전이 | 단일 promotion executor 또는 명시적 lock·CAS | 여러 map과 queue의 부분 변경 방지 |
| Redis Pub/Sub | 프로세스 내부 event publisher | 같은 JVM의 SSE 연결에 상태 변경 전달 |

`ConcurrentHashMap`은 동시 접근을 안전하게 만들지만 순번을 제공하지 않는다. 순번 정렬과 범위 조회에는 `ConcurrentSkipListMap` 같은 정렬 자료구조가 필요하다. `lastKey() + 1`은 동시 join에서 안전하지 않으므로 순번은 `AtomicLong`이 맡아야 한다.

활성 세션 수만 제한하는 경우에는 `Semaphore`를 사용할 수 있다. 입장권 lease 만료·완료·취소에서 permit을 정확히 한 번 반환해야 하며, 프로세스 재시작 뒤 permit과 ticket 상태를 함께 복구해야 한다. 회차별 `admitPerInterval`은 시간 창과 카운터가 필요하므로 `Semaphore` 하나로 대체되지 않는다.

## 4. 메모리 대안의 동작 경계

예시 흐름은 다음과 같다.

```text
join
  → AtomicLong.incrementAndGet()
  → ticket 상태 생성
  → waiting 정렬 map·deadline queue·owner map 등록

status
  → ticket map 조회
  → WAITING이면 순번 map에서 rank 계산

promotion
  → 만료 task 정리
  → active 세션 상한 확인
  → waiting 첫 항목 제거
  → ticket 상태를 ADMITTED로 변경
  → active lease와 SSE 이벤트 등록

complete/cancel/expire
  → ticket·waiting·deadline·active·owner를 함께 정리
```

각 자료구조의 메서드가 thread-safe여도 여러 자료구조의 변경이 하나의 원자적 작업이 되지는 않는다. 예를 들어 ticket 상태를 `ADMITTED`로 바꾼 뒤 active map 등록 전에 프로세스가 중단되면 상태와 인덱스가 달라진다. 한 스케줄러가 승급을 직렬화하거나, 명시적인 lock·CAS 규칙으로 전이를 묶어야 한다.

`ConcurrentSkipListMap`에서 현재 순번을 계산할 때 `headMap(sequence).size()`를 사용하면 대기열 전체 크기에 비례하는 비용이 생길 수 있다. Redis `ZRANK`와 같은 순위 연산을 JVM map이 자동으로 제공하지 않으므로, 정확한 순번 조회 빈도와 대기열 크기에 따른 CPU 비용을 별도로 측정해야 한다.

## 5. 단일 서버에서 얻는 이점

- Redis 네트워크 왕복과 직렬화 비용이 사라진다.
- join·status·promotion의 프로세스 내부 지연을 낮출 수 있다.
- 외부 저장소 없이 작은 개발·검증 환경을 구성할 수 있다.
- 자료구조와 상태 전이를 직접 구현하며 Waiting Room 계약을 학습하기 쉽다.

이 이점은 하나의 프로세스가 상태의 소유권을 가지고, 메모리 한도와 재시작 정책이 명확할 때 유효하다.

## 6. 제품 경로에서 남는 비용

| 검토 항목 | 메모리 대기열에서 필요한 처리 |
|---|---|
| 재시작·배포 | 대기 ticket과 순번을 잃는다. 재가입·복구 정책을 별도로 정해야 한다. |
| 수평 확장 | 인스턴스별 queue가 갈라진다. 전역 순번과 active 상한을 공유하지 못한다. |
| 재연결 | 다른 인스턴스가 ticket과 SSE 연결을 찾을 수 있도록 sticky session 또는 공유 저장소가 필요하다. |
| 원자성 | ticket·owner·순번·만료·active를 함께 바꾸는 애플리케이션 동기화가 필요하다. |
| 메모리 | 대기 ticket, 만료 task, SSE 연결, 이벤트가 JVM heap을 사용한다. GC와 OOM을 관측해야 한다. |
| 순번 조회 | 정렬 map의 rank 계산 비용과 status polling CPU를 측정해야 한다. |
| 장애 전환 | 서버 교체 뒤 기존 입장권과 대기 순서의 유효성을 결정해야 한다. |

## 7. 선택 기준

| 조건 | 메모리 대기열을 검토할 수 있는 경우 | Redis를 유지해야 하는 경우 |
|---|---|---|
| 실행 규모 | Waiting Room Service 한 인스턴스 | 여러 인스턴스 또는 자동 장애 전환 |
| 상태 수명 | 재시작 시 유실과 재가입을 허용 | 배포·재시작 뒤 ticket 복구 필요 |
| 사용자 경험 | 정확한 순번·재접속 연속성이 낮은 임시 대기 | 순번, 상태, entry pass 연속성이 중요 |
| 상태 전이 | 단일 executor로 전이를 직렬화할 수 있음 | 여러 인스턴스의 join·promotion·complete가 동시에 실행 |
| 운영 목표 | 개발·교육·짧은 이벤트 | 운영 후보 부하, 장애 복구, 공유 상태 검증 |

현재 ImTicket은 오른쪽 조건에 해당한다. 따라서 Redis를 유지하고, 메모리 자료구조는 비교 기준선과 단일 서버 실험 후보로 남긴다.

## 8. 다시 검토할 때의 측정 순서

메모리 대안을 실제로 비교할 때는 `WaitingRoomStore` 계약 뒤에 별도 구현을 두고 같은 시나리오를 실행한다.

1. 한 인스턴스에서 2,000명 join burst와 status polling을 실행한다.
2. join p95, status p95, promotion 지연, rank 계산 CPU, heap·GC를 측정한다.
3. 동일 회원 중복 join, cancel·expire·complete 동시 실행에서 map과 queue의 일치 여부를 확인한다.
4. promotion 중 프로세스 종료와 재기동 뒤 복구 결과를 기록한다.
5. 두 인스턴스와 재연결을 추가해 전역 순번·active 상한·SSE 상태 차이를 확인한다.

측정 결과가 재시작 유실, 인스턴스 간 상태 불일치, 순번 조회 비용을 허용 범위 안에 두면 단일 서버 프로파일을 별도로 제공할 수 있다. 현재 문서는 운영 적용과 HTTP 전체 흐름 성능 결과를 포함하지 않는다.

## 9. 2,000명 비교 결과

테스트 전용 `InMemoryWaitingRoomStore`를 작성하고 현재 `WaitingRoomStore` 계약의 join·status·promotion 시나리오를 실행했다. Redis 비교는 같은 JVM 테스트 프로세스에서 loopback Redis 8.6.0을 사용했다. join과 status는 32개 worker가 2,000건을 나누어 실행했고, promotion은 50명 batch를 40회 순차 호출했다. status 한 건의 측정 범위는 ticket 조회와 현재 순번 조회다.

핵심 계약 테스트와 메모리 전용 동시성·다중 인스턴스 한계 테스트, Redis 통합 계약 테스트가 모두 통과했다. 아래 표는 같은 비교 테스트의 한 번 실행에서 수집한 값이며, p50·p95는 개별 연산 지연 시간, 처리량은 전체 wall-clock 시간 기준이다.

| 저장소 | 연산 | 건수 | p50 (µs) | p95 (µs) | 처리량 (op/s) |
|---|---|---:|---:|---:|---:|
| 메모리 | join | 2,000 | 5.21 | 2,032.33 | 78,191.18 |
| Redis | join | 2,000 | 3,675.13 | 8,550.00 | 6,370.95 |
| 메모리 | status (`find` + rank) | 2,000 | 17.63 | 4,828.67 | 42,974.32 |
| Redis | status (`find` + rank) | 2,000 | 1,558.13 | 3,507.04 | 17,230.53 |
| 메모리 | promotion (50명 batch) | 40 | 153.46 | 546.63 | 4,330.47 |
| Redis | promotion (50명 batch) | 40 | 9,996.04 | 21,089.79 | 79.34 |

메모리는 네트워크·직렬화 비용이 없어 join과 promotion의 지연이 낮았다. status p95는 Redis보다 낮지 않았고, 순번을 계산하는 `headMap(sequence).size()`와 회차 lock 경합이 tail에 반영됐다. 메모리 구현은 한 프로세스 안에서 빠른 기준선을 제공하면서 정확한 rank와 상태 전이에 필요한 CPU·동기화 비용을 남긴다.

초기 비교 실행에서는 고정 thread pool이 2,000개 작업의 준비 장벽을 기다려 30초 timeout이 발생했다. worker가 작업 범위를 나누어 실행하도록 측정기를 수정했다. 계약 테스트 컴파일에서 `Instant.plusMinutes` 호출도 확인되어 `plus(Duration.ofMinutes(...))`로 수정했고, 수정 후 관련 테스트를 다시 통과시켰다.

실행기와 계약 테스트는 다음 파일에 있다.

- [WaitingRoomStorePerformanceComparisonTest](../../../src/test/java/org/example/ticket/reservation/waitingroom/repository/WaitingRoomStorePerformanceComparisonTest.java)
- [InMemoryWaitingRoomStore](../../../src/test/java/org/example/ticket/reservation/waitingroom/repository/inmemory/InMemoryWaitingRoomStore.java)
- [InMemoryWaitingRoomStoreTest](../../../src/test/java/org/example/ticket/reservation/waitingroom/repository/inmemory/InMemoryWaitingRoomStoreTest.java)

재현 명령은 전용 Redis를 16380 포트에서 실행한 뒤 다음과 같이 사용한다.

```bash
redis-server --port 16380 --save "" --appendonly no --daemonize yes

WAITING_ROOM_REDIS_BENCHMARK=true \
WAITING_ROOM_REDIS_HOST=127.0.0.1 \
WAITING_ROOM_REDIS_PORT=16380 \
./gradlew test --tests \
  'org.example.ticket.reservation.waitingroom.repository.WaitingRoomStorePerformanceComparisonTest'

redis-cli -p 16380 shutdown nosave
```

계약만 재현할 때는 `./gradlew test --tests 'org.example.ticket.reservation.waitingroom.repository.inmemory.InMemoryWaitingRoomStoreTest'`를 실행한다. Redis 계약은 같은 포트에서 `WAITING_ROOM_REDIS_TEST_ENABLED=true`를 추가하고 `org.example.ticket.reservation.waitingroom.repository.redis.RedisWaitingRoomStoreIntegrationTest`를 지정한다.

이 표는 애플리케이션 HTTP·Nginx·SSE·MySQL을 포함하지 않는 저장소 연산 비교다. 운영 용량 판단에는 같은 입력률의 HTTP 전체 흐름과 재시작·다중 인스턴스 시험을 추가해야 한다.

## 10. embedded Tomcat API 비교 결과

저장소 호출만 비교한 결과가 실제 요청 경로에서도 유지되는지 확인하기 위해 테스트 전용 Spring Boot context를 만들었다. `WaitingRoomController`와 `WaitingRoomService`를 embedded Tomcat에 연결하고, `X-Test-Member-Id`를 사용하는 테스트 principal resolver를 등록했다. join·status 요청을 32개 client worker로 각각 2,000건 보냈다. Tomcat `server.tomcat.threads.max`는 32로 고정했다. 서버 최대값은 테스트 filter가 관측한 API handler 동시 실행 수다.

| 저장소 | API | 건수 | p50 (ms) | p95 (ms) | 처리량 (req/s) | client in-flight 최대 | server handler 최대 | HTTP 2xx |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 메모리 | `POST /join` | 2,000 | 10.979 | 25.519 | 2,037.94 | 32 | 32 | 2,000 |
| Redis | `POST /join` | 2,000 | 16.835 | 46.413 | 1,333.92 | 32 | 32 | 2,000 |
| 메모리 | `GET /tickets/{ticketId}` | 2,000 | 8.939 | 18.069 | 3,186.54 | 32 | 28 | 2,000 |
| Redis | `GET /tickets/{ticketId}` | 2,000 | 15.188 | 46.079 | 1,481.38 | 32 | 32 | 2,000 |

embedded Tomcat API에서도 메모리 저장소의 join·status p95와 처리량이 더 낮은 지연을 보였다. join은 양쪽 모두 handler 동시 실행 최대 32에 도달했다. status에서는 메모리 실행의 handler 최대가 28, Redis 실행이 32였으며, 저장소 응답 시간이 Tomcat worker 점유 시간에 영향을 주는 흐름을 확인했다.

이 비교의 server handler 최대는 실제 운영 Tomcat의 전체 스레드 사용률이나 Nginx 연결 수를 뜻하지 않는다. 설정된 Tomcat 최대 스레드 32와 테스트 filter에서 관측한 API 실행 동시성을 함께 기록한 값이다. Nginx·SSE·MySQL·좌석 선점은 포함하지 않는다.

실행기는 [WaitingRoomApiPerformanceComparisonTest](../../../src/test/java/org/example/ticket/reservation/waitingroom/api/WaitingRoomApiPerformanceComparisonTest.java)다. 초기 실행에서 운영 `application.properties`가 테스트 기본 설정을 덮어써 Waiting Room이 비활성화됐고, Actuator 관리 보안 자동 설정이 `HttpSecurity`를 요구했으며, 컨트롤러 경로가 404로 반환됐다. 테스트 context의 설정 위치를 격리하고 관리 보안을 제외했으며 컨트롤러를 명시적 Bean으로 등록해 해결했다. 수정 후 메모리·Redis API 비교 모두 HTTP 2xx 2,000건을 통과했다.

메모리 API 기준선은 `./gradlew test --tests 'org.example.ticket.reservation.waitingroom.api.WaitingRoomApiPerformanceComparisonTest'`로 실행한다. Redis API 비교는 전용 Redis를 실행한 뒤 `WAITING_ROOM_REDIS_BENCHMARK=true`와 host·port 환경 변수를 설정하고 같은 테스트를 `--rerun-tasks`로 실행한다.

## 11. 포트폴리오용 의사결정 문장

> 단일 서버 기준으로 `AtomicLong`, `ConcurrentSkipListMap`, `ConcurrentHashMap`을 조합한 메모리 Waiting Room도 검토했다. 프로세스 내부 지연은 줄일 수 있지만 재시작 복구, 다중 인스턴스 공유, 정확한 순번 조회, 여러 자료구조의 원자적 상태 전이를 별도로 설계해야 한다. 현재 ImTicket은 공유 상태와 복구 계약을 우선해 Redis ZSET·Hash·Lua를 유지하고, 메모리 구조는 단일 서버 프로토타입과 비교 기준선으로 기록했다.
