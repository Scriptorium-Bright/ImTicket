# Waiting Room 의사결정 로그

작성일: 2026-09-04

갱신일: 2026-09-10

기준일: 2026-09-03  
상세 기준: [통합 안내](../../portfolio/lock-to-waiting-room-reading-guide.md) · [ADR](146.12-waiting-room-admission-boundary-adr.md) · [전체 흐름](146.14-waiting-room-flow.md)

이 문서는 지금까지의 주요 가설, 관찰 근거, 결정, 다음 검증을 한 페이지에서 확인하기 위한 요약 로그다.

| 단계 | 질문·가설 | 근거 | 결정 | 다음 확인 |
|---|---|---|---|---|
| 1. 좌석 정합성 | 같은 좌석을 동시에 요청해도 하나만 성공해야 하는가 | DB transaction, 좌석 잠금, idempotency 경계가 이미 존재 | 좌석 선점은 동기 처리 | 성공 1건·409 N-1·conflict latency |
| 2. 대기열 도입 | burst 사용자를 예약 서버까지 모두 전달해도 되는가 | origin 보호와 active session 상한이 필요 | Redis ZSET·Hash·Lua Waiting Room 채택 | queue contract·순번·만료·capacity |
| 3. Tomcat 포화 | 병목의 중심이 예약 로직 자체인가 | 직통 2,000 burst에서 busy 200 | ingress 유입량을 먼저 제어 | Gateway 전달률과 origin 지표 |
| 4. Streams async join | join을 worker concurrency 뒤로 이동했는가 | A1·A2 모두 2,000건 계약 성공, Tomcat busy 200; A2 수락 p95 1,454.3ms, A1 p95 1,124.0ms | `e2f4150`에서 제거 완료 | 실제 join 처리를 작업자가 담당하는 새 구조일 때만 재검토 |
| 5. Gateway 실험 | ingress 경계가 origin을 보호하는가 | Gateway busy 57~75, 별도 Waiting Room 뒤 origin busy 30~32, Hikari pending 0 | Nginx + 별도 Waiting Room Service 유지 | 동기 A1을 `10082` Gateway로 재현 |
| 6. 상태 전달 | 순번·입장 상태를 어떻게 전달할 것인가 | polling은 반복 status 요청, SSE는 상태 변경 push 구조 | Ticket SSE 유지, polling fallback 유지 | SSE·폴링 인지 지연과 자원 비교 |
| 7. admission 값 | 어떤 활성 세션 상한이 예약 애플리케이션을 보호하는가 | 상한 50에서 HikariCP 대기 20, 상한 30에서 대기 0 | `maxActiveSessions=30` 유지 | 현재 전체 흐름 용량과 분리해 관리 |
| 8. promotion | scheduler가 실제 입장률을 제한하는가 | 주기당 25명 설정에서 실제 처리율 13.06~16.09명/s, 후보별 `HGETALL` 왕복 관찰 | 기존 batch Lua 유지, 후보 조회 pipeline 제안 | Redis 왕복·scheduler 시간·queue wait 비교 |
| 9. 메시지 버스 | 좌석 현황 전파에 내구성 메시지가 필요한가 | 2026-09-01 도입 게이트 다섯 항목 미충족 | 현재 커밋 이후 무효화 유지 | 최신성·독립 소비자·자동 재처리 요구 발생 시 재검토 |
| 10. 검증 순서 | 무엇을 더 측정해야 하는가 | 2026-08-24의 2,000명 3회 종료 조건 통과, 캐시 통합 뒤 2,000 VU 용량 기준 실패 | 1,500 VU를 보수적 업무 흐름 기준선으로 기록 | 별도 부하 발생기와 scheduler 개선 뒤 최종 용량 확정 |
| 11. 구성 정렬 | join 경로가 하나로 정리됐는가 | Streams 작업자·설정·join-request SSE 참조 0건 | 동기 join 단일 경로 확정 | 최종 반복에서 계약 확인 |
| 12. 동일 좌석 경합 | 같은 좌석에서 승자 한 명과 충돌 응답을 보장하는가 | Gateway·entry pass를 포함한 10·100명 실행에서 성공 1건, `409` N-1건, 충돌 p95 3.37초, deadlock 0건 | 정합성·종료 SLO 5초 통과 | 잠금 코드 변경 시에만 재검증 |
| 13. 단일 서버 메모리 대안 | Waiting Room Service 한 대에서 Redis를 대체할 수 있는가 | `AtomicLong`·`ConcurrentSkipListMap`·`ConcurrentHashMap` 조합은 가능하지만 재시작·다중 인스턴스·원자적 다중 상태 전이를 별도로 해결해야 함 | 현재 Redis 유지, 메모리 구조는 단일 서버 프로토타입·비교 기준선으로 기록 | 재시작 유실을 허용하는 단일 서버 프로파일이 필요할 때 동일 계약으로 측정 |

## 현재 증거 묶음

```text
직통 2,000 burst
  → Reservation Application Tomcat busy max 200

Gateway 전달률 제한
  → origin Tomcat busy 57~75
  → Hikari pending 거의 0

Waiting Room 별도 서비스
  → origin Tomcat busy 30~32
  → Hikari pending 0

동기 API 계약 E2E
  → contract success 1
  → join 228ms
  → queue wait 975ms
  → seat map 860ms
  → pre-reserve 565ms

A1·A2 join 비교, 본 측정 3회
  → A1 계약 성공 6,000 / 6,000
  → A2 계약 성공 6,000 / 6,000
  → A1 p95 평균 1,124.0ms
  → A2 수락 p95 평균 1,454.3ms
  → A2 ticket 완료 p95 평균 1,464.3ms
  → 양쪽 Tomcat busy max 200

B 고유 좌석 용량, 최신 실행 20260820T084841Z
  → 동시 사용자 10·20·30·40·50 계약 성공 100%
  → pre-reserve 성공 150 / 150
  → Hikari pending max 0
  → 50명 구간 seat map p95 313.7ms
  → 50명 구간 pre-reserve p95 528.4ms

C 동일 좌석 경합, 최신 실행 20260824T104309Z
  → 동시 사용자 10·100 계약 성공 100%
  → 성공 2 / 2, 충돌 108 / 108
  → 100명 구간 성공 p95 1,336.132ms
  → 100명 구간 충돌 p95 3,367.930ms, p99 3,427.402ms
  → 100명 구간 Hikari pending max 42
  → MySQL row lock wait max 0, deadlock 0
```

## 현재 작업 상태

- `eb0a820`: A1 동기 join 실행 도구와 검증 보완
- `1c2accf`: Nginx Waiting Room Gateway와 Compose 구성
- A1·A2 비교 결과: [2026-08-20 비교 문서](../../test/2026-08-20-waiting-room-a1-a2-comparison.md)
- 동기 A1 `10082` Gateway 경유 3회 완료: `200` 응답 6,000건, 계약 성공률 100%
- B 최신 실행: `20260820T084841Z`, 10·20·30·40·50명 전 구간 통과
- C 동일 좌석 경합 정합성 완료: [C 결과 문서](../../test/2026-08-24-waiting-room-c-same-seat-contention.md)
- `e2f4150`: 비동기 join 인계·join-request SSE 제거, 동기 프런트 흐름 정리
- `6bcc203`: 비동기 전용 테스트 제거, 동기 검증 실행기 정리
- 제거 후 백엔드 전체 테스트·프런트엔드 빌드·1명 핵심 E2E 통과
- 2026-08-24 종료 시험: 2,000명 전체 흐름 3회 계약 100%, Reservation Application Tomcat busy 최대 30, HikariCP 대기 0
- 캐시 통합 뒤 용량 재검증: 2,000 VU 기준 미충족, 1,500 VU 업무 흐름 통과
- 현재 다음 실행: 승급 후보 조회 pipeline 대조 시험과 별도 부하 발생기 용량 재검증

## 결정 갱신 규칙

측정 결과가 기존 결정을 바꿀 때는 다음 순서로 기록한다.

```text
관찰값
  → 기존 가설과의 차이
  → 영향받는 책임 경계
  → 결정 변경 또는 유지
  → 재현 명령과 결과 파일
```

운영값만 바뀌면 ADR의 검증 결과와 설정 근거를 갱신한다. 책임 경계가 바뀌면 ADR의 결정과 전체 흐름을 함께 갱신한다.
