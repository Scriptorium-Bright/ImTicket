# 146.16 Waiting Room 저장소·대기열 대안 의사결정

작성일: 2026-08-25  
상태: 현재 결정 정리  
상위 결정: [Waiting Room ADR](146.12-waiting-room-admission-boundary-adr.md)  
현재 흐름: [Waiting Room 전체 흐름](146.14-waiting-room-flow.md)

## 1. 결론

ImTicket Waiting Room은 다음 조합을 사용한다.

```text
Nginx Gateway
  → 별도 Waiting Room Service
  → Redis ZSET·Hash·Lua
  → Ticket SSE + 상태 조회 복구
  → entry pass
  → Reservation Application
```

Redis ZSET은 순번과 시간 기준 조회를 담당하고, Hash는 ticket 상태를 저장하며, Lua는 join·promotion·만료 전이를 원자적으로 처리한다. Nginx와 별도 Waiting Room Service는 예약 애플리케이션에 도달하는 요청량과 실행 자원을 분리한다.

Java 메모리 큐, 관계형 데이터베이스, Redis List, Redis Streams, Kafka, 관리형 Waiting Room을 같은 요구사항으로 비교한 결과 현재 프로젝트의 순번·상태·만료·다중 인스턴스 계약에는 Redis ZSET·Hash·Lua가 가장 직접적으로 맞는다.

## 2. Waiting Room이 제공해야 하는 계약

Waiting Room은 단순한 선입선출 작업 큐보다 많은 상태 조회를 제공한다.

| 계약 | 필요한 동작 |
|---|---|
| 회차별 순번 | sequence 발급, rank 조회, 앞 순번 promotion |
| 중복 join 방지 | owner와 ticket의 1:1 mapping |
| 대기열 용량 | join 시 최대 대기 인원 확인 |
| 대기 만료 | deadline 이전·이후 ticket 조회와 정리 |
| 활성 세션 상한 | `maxActiveSessions`와 active lease 관리 |
| 입장률 | 주기별 `admitPerInterval` 적용 |
| 상태 조회 | `WAITING`, `ADMITTED`, `EXPIRED`, `COMPLETED` 조회 |
| 재연결 | 동일 owner의 ticket과 entry pass 복구 |
| 다중 인스턴스 | 어느 instance에서도 같은 순번과 상태 조회 |
| 원자성 | join·promotion 중복과 부분 상태 방지 |
| 서버 재시작 | Waiting Room Service 재시작 후 상태 유지 |

이 요구사항을 기준으로 자료구조와 실행 경계를 선택한다.

## 3. 대안 비교

| 대안 | 순번·rank | 만료·lease | 다중 인스턴스 | 원자적 상태 전이 | 재시작 유지 | 현재 적합성 |
|---|---|---|---|---|---|---|
| Java `ArrayBlockingQueue` | dequeue 순서 | 별도 scheduler·map | instance별 분리 | lock과 보조 map 필요 | 메모리 유실 | 단일 instance·임시 queue |
| Java `PriorityBlockingQueue` | score 순서 | deadline 정렬 가능 | instance별 분리 | bounded capacity·dedupe 별도 | 메모리 유실 | 단일 process scheduler |
| MySQL queue table | sequence·index | timestamp·query | 공유 가능 | transaction | 유지 | 내구성 우선·낮은 burst |
| Redis List | enqueue·dequeue | 별도 key 필요 | 공유 가능 | Lua 가능 | Redis persistence | 단순 FIFO |
| Redis ZSET·Hash·Lua | `ZRANK`·score | deadline·active ZSET | 공유 가능 | Lua | Redis persistence | 현재 Waiting Room |
| Redis Streams | entry 순서 | pending·idle 중심 | consumer group | stream 연산 | retention | 비동기 작업 전달 |
| Kafka | partition log 순서 | 별도 상태 저장소 | consumer group | 상태 projection 필요 | log retention | 대규모 event log |
| 관리형 Waiting Room | 제품별 제공 | 제품별 제공 | edge·managed | 제품 계약 | 관리형 | 운영 edge 보호 |

## 4. Java 메모리 큐를 선택할 수 있는 경우

### 4.1 `ArrayBlockingQueue`

`ArrayBlockingQueue`는 고정 용량, 낮은 프로세스 내부 지연, 선입선출 dequeue를 제공한다. 다음 조건의 작은 시스템에는 충분하다.

- Waiting Room Service가 한 instance다.
- 재시작 시 대기 상태 유실을 허용한다.
- 사용자가 순번과 재연결 상태를 조회하지 않는다.
- queue item을 꺼내 즉시 작업하는 worker 구조다.
- sticky session과 instance 장애 전환이 필요하지 않다.

ImTicket 계약을 구현하려면 queue 이외에 다음 상태가 추가된다.

```text
ArrayBlockingQueue<ticketId>
ConcurrentHashMap<owner, ticketId>
ConcurrentHashMap<ticketId, TicketState>
DelayQueue<deadline>
active session set
sequence counter
각 자료구조를 함께 변경하는 lock
```

이 구조는 한 JVM 안에서 동작한다. instance가 둘 이상이면 전역 순번, owner dedupe, active session 상한이 instance마다 달라진다. 재시작 후 owner와 ticket 복구도 별도 영속화가 필요하다.

### 4.2 `PriorityBlockingQueue`와 `DelayQueue`

`PriorityBlockingQueue`는 sequence 또는 priority 순서 처리에 사용할 수 있고, `DelayQueue`는 만료 시점 처리를 지원한다. 두 queue와 상태 map을 함께 사용할 때 join·promotion·cancel의 원자성을 애플리케이션 lock으로 설계해야 한다.

Java queue는 단일 instance 성능 기준선이나 교육용 구현으로 가치가 있다. 현재 제품 흐름의 공유 상태 저장소에는 Redis를 사용한다.

## 5. 관계형 데이터베이스 queue

MySQL table로 ticket, owner, sequence, deadline, active lease를 저장하면 transaction과 영속성을 사용할 수 있다.

예시:

```text
waiting_room_ticket
  performance_time_id
  ticket_id
  owner_id
  sequence
  status
  waiting_deadline
  entry_expires_at
```

장점:

- DB transaction과 unique constraint 사용
- 서버 재시작과 장애 후 상태 유지
- 운영 백업·복구 절차 활용
- SQL을 통한 감사·조회

측정 대상:

- 2,000명 burst의 INSERT·UPDATE latency
- `(performance_time_id, status, sequence)` index 경합
- rank 계산과 promotion query 비용
- cleanup·lease query 비용
- Waiting Room DB pool과 Reservation DB pool의 자원 분리

Waiting Room burst가 예약 데이터베이스와 같은 connection budget을 사용하면 보호 대상의 HikariCP·MySQL 자원을 다시 소비한다. 별도 DB·pool을 두면 운영 구성과 복제·장애 전환 범위가 늘어난다.

## 6. Redis 자료구조별 판단

### 6.1 Redis List

List는 `LPUSH/RPOP` 또는 `RPUSH/LPOP`으로 단순 FIFO를 구현하기 쉽다. 현재 계약의 rank, 임의 ticket cancel, deadline 범위 조회, active lease는 별도 key와 scan·index가 필요하다.

### 6.2 Redis ZSET·Hash·Lua

현재 구조는 역할을 다음과 같이 나눈다.

| 자료구조 | 역할 |
|---|---|
| waiting ZSET | sequence score, `ZRANK`, 앞 순번 조회 |
| deadline ZSET | 만료 epoch score, 범위 정리 |
| active ZSET | entry lease 만료, active session 수 |
| ticket Hash | owner, 회차, 상태, sequence, pass 만료 |
| owner mapping | 중복 join 방지와 재연결 |
| Lua | join·promotion·cancel·complete의 원자적 변경 |

장점:

- 다중 Waiting Room instance가 같은 상태를 조회
- 회차별 순번과 시간 index를 같은 Redis에서 관리
- Lua 한 번으로 여러 key의 상태 전이
- 서비스 재시작 뒤 ticket 복구
- SSE 연결 instance와 상태 소유권 분리

운영 검증 항목:

- Redis persistence와 failover
- eviction 0과 `maxmemory` 여유
- hot performance key의 command latency
- Lua 실행 시간과 scheduler 지연
- backup·restore 뒤 ticket·ZSET·mapping 일치

### 6.3 Redis Streams

Streams는 작업을 consumer에게 전달하고 ACK·pending·재처리를 관리하는 데 적합하다. Waiting Room 사용자는 현재 순번, 상태, deadline, entry pass를 반복 조회한다. 이 조회 계약에는 ZSET과 Hash가 계속 필요하다.

과거 async join 구현에서는 HTTP 요청의 Lua가 ticket과 Waiting ZSET을 이미 생성했고 Worker는 처리 상태와 알림을 기록했다. A1·A2 비교에서 origin 유입량 제어 효과가 확인되지 않아 해당 경로를 제거했다.

Streams는 promotion 이후 실제 비동기 작업이 생길 때 다시 검토한다.

## 7. Kafka를 Waiting Room에 적용하는 경우

Kafka는 대규모 event log, replay, consumer group, partition 단위 순서를 제공한다. Waiting Room을 Kafka 중심으로 구성하면 현재 상태를 조회하기 위한 materialized state가 추가로 필요하다.

```text
JoinRequested topic
  → partition별 consumer
  → WaitingRoom state projection
  → status store
  → rank·deadline·active lease API
```

설계 항목:

- 같은 회차의 partition key와 hot partition
- 전역 rank 또는 partition별 rank의 의미
- owner dedupe와 ticket 조회 저장소
- event 처리 지연과 HTTP join 응답 계약
- consumer rebalance 중 promotion 중복 방지
- 상태 projection rebuild와 entry pass 복구

Kafka는 장기 replay와 여러 downstream consumer가 핵심 요구가 되는 event 기반 Waiting Room에서 후보가 된다. 현재 ImTicket은 순번·상태·만료를 직접 조회하는 단일 region 구조이므로 Redis 상태 모델을 사용한다.

## 8. 관리형 Waiting Room과 Nginx

### 8.1 관리형 Waiting Room

Cloudflare Waiting Room, Queue-it과 같은 관리형 제품은 edge에서 사용자를 보유하고 origin으로 들어오는 신규 사용자 수와 활성 세션 수를 제어한다.

적합 조건:

- 대규모 공개 서비스에서 origin 연결 이전 차단이 필요하다.
- 다중 region, DDoS 대응, 장애 전환을 운영 요구로 둔다.
- 자체 순번·토큰·재연결 시스템의 운영 비용을 줄여야 한다.

### 8.2 Nginx 요청률 제한

Nginx는 Waiting Room Service로 전달하는 요청률을 제한해 HTTP worker를 보호한다. 사용자별 순번, ticket 상태, 재연결, entry pass는 Waiting Room Service가 관리한다.

현재 구성은 Nginx의 유입량 제어와 Redis Waiting Room의 사용자 상태 관리를 결합한다.

## 9. 현재 의사결정과 근거

| 질문 | 근거 | 결정 |
|---|---|---|
| 프로세스 내부 queue로 충분한가 | 재연결, 다중 instance, 서버 재시작 후 상태 유지 필요 | 공유 Redis 상태 사용 |
| List로 순번을 관리할 수 있는가 | rank·deadline·active lease·임의 상태 조회 필요 | ZSET·Hash 사용 |
| Streams가 join을 가볍게 만드는가 | HTTP Lua에서 ticket·Waiting ZSET 생성 완료, Worker의 실제 join 작업이 작음 | 동기 join 유지 |
| Kafka가 rank와 entry pass를 제공하는가 | 별도 state projection과 status store 필요 | 현재 Waiting Room state store로 사용하지 않음 |
| Redis만으로 origin을 보호하는가 | 직접 2,000 join에서 Tomcat busy 200 | Nginx와 별도 Waiting Room Service 결합 |
| 현재 구조가 예약 서버를 보호하는가 | Gateway busy 57~75, 별도 서비스 뒤 origin busy 30~32·HikariCP pending 0 | 현재 구성 유지 |

## 10. 재검토 조건

- 단일 instance와 재시작 유실 허용 조건이면 Java bounded queue를 비교한다.
- Waiting Room 상태를 장기 replay해야 하고 다수 소비자가 필요하면 Kafka event log와 state projection을 비교한다.
- 실제 비동기 작업 전달과 consumer ACK·pending 복구가 필요하면 Redis Streams를 비교한다.
- Redis memory·failover 요구가 현재 운영 범위를 넘으면 관리형 Waiting Room 또는 별도 Redis 구성을 비교한다.
- 다중 region의 공정성과 전역 순번이 필요하면 edge 기반 admission과 region별 queue 정책을 별도 설계한다.

## 11. 포트폴리오용 의사결정 문장

> Waiting Room은 선입선출 dequeue만 수행하는 작업 큐가 아니라 순번·중복 join·대기 만료·활성 세션·재연결 상태를 조회하는 시스템이었습니다. Java bounded queue, MySQL, Redis List, Redis Streams, Kafka를 같은 계약으로 비교했고, `ZRANK`와 시간 score, 다중 key 원자 전이가 필요한 현재 구조에는 Redis ZSET·Hash·Lua를 선택했습니다. Nginx와 Waiting Room Service를 분리한 뒤 예약 애플리케이션 Tomcat busy 최대값은 200에서 30~32로 낮아졌고 HikariCP pending은 0을 유지했습니다.

단일 서버 메모리 자료구조의 구체적인 대응, `ConcurrentSkipListMap`의 순번 조회 비용, 재검토 측정 순서는 [146.18 단일 서버 메모리 Waiting Room 대안 의사결정](146.18-single-server-memory-queue-decision.md)에서 이어서 확인한다.
