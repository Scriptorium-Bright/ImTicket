# Phase 3 계획: 생명주기 재구성

작성일: 2026-09-20(KST)  
상태: 부분 완료  
상위 계획: [구현 계획 7절](../../implementation-plan.md#phase-3-lifecycle-재구성)  
실행 결과: [Phase 3 결과](result.md)
상세 규칙: [생명주기 재구성 명세](../../lifecycle-reconstruction-spec.md)

## 1. 왜 수행하는가

Phase 2의 사건 원본만으로는 개발자와 운영자가 예약·결제 상태와 실행 경로를 즉시 확인할 수 없다. Phase 3은 커밋 사건을 결정 순서대로 적용해 네 상태 축, 사건 이력, 실행 경로와 데이터 신뢰 상태를 가진 조회 모델을 만든다.

재구성 규칙은 전달 순서와 실행 시각에 영향을 받지 않아야 하며, 같은 사건 입력에서 항상 같은 결과를 만들어야 한다.

## 2. 시작 조건

- Phase 2가 정상 커밋 사건 누락 0건, 롤백 사건 0건으로 완료돼 있다.
- 여섯 사건의 코드 계약과 JSON 스키마가 고정돼 있다.
- `decisionVersion`, `eventOrdinal`, `commitGroupId`가 경로 A/B 데이터에서 검증돼 있다.
- Poller가 `(lifecycleId, decisionVersion)` 단위로 사건 전체를 읽을 수 있다.
- [데이터 모델과 ERD](../../data-model-erd.md)의 조회 모델 물리 스키마와 보존 정책을 검토할 MySQL 용량 기준선이 있다.

## 3. 변경 범위

### 3.1 조회 모델 스키마

논리 책임은 다음과 같이 나눈다. 물리 테이블 수는 스키마 설계에서 확정한다.

| 논리 모델 | 저장 내용 | 주요 키 |
| --- | --- | --- |
| 생명주기 요약 | Reservation·PaymentOrder 상태, 경로, 신뢰 상태, 마지막 적용 버전 | `lifecycleId`, `reservationId`, `paymentOrderId` |
| 좌석 상태 | 생명주기에 연결된 좌석별 현재 상태 | `lifecycleId`, `seatId` |
| 결제 시도 상태 | 시도별 상태, 승인 시각과 거래 식별자 | `lifecycleId`, `paymentAttemptId` |
| 사건 적용 기록 | 적용한 `eventId`, 결정 버전, 조회 모델 버전 | `eventId`, `projectionVersion` |
| 원천 대조 결과 | 마지막 대조 시각, 원천·조회 버전과 필드 차이 | `lifecycleId` |

조회 모델은 사건 원본에서 재생할 수 있어야 한다. 사건 적용 기록과 상태 갱신은 같은 데이터베이스 트랜잭션으로 커밋한다.

### 3.2 결정적 재구성기

재구성 로직은 [생명주기 재구성 명세](../../lifecycle-reconstruction-spec.md)의 입출력, 결정 단위 불변 조건과 상태 전이 규칙으로 구현한다.

```text
입력: 현재 LifecycleSnapshot + 같은 decisionVersion의 정렬된 사건
출력: 다음 LifecycleSnapshot + 적용 사건 기록 + 경로 분류 후보
```

적용 순서는 다음과 같다.

1. `lifecycleId`와 `decisionVersion`을 확인한다.
2. 동일 `eventId`와 이미 적용한 결정인지 확인한다.
3. 기대하는 다음 버전인지 확인한다.
4. 같은 버전의 사건을 `eventOrdinal`로 정렬한다.
5. `commitGroupId`와 필수 사건 조합을 검증한다.
6. `stateChanges`의 변경 전 상태가 현재 상태와 일치하는지 확인한다.
7. 네 상태 축을 갱신한다.
8. 경로 분류와 신뢰 상태를 계산한다.
9. 적용 기록과 조회 모델을 함께 커밋한다.

사건 계약 위반이나 변경 전 상태 불일치는 자동으로 덮어쓰지 않는다. 적용을 중단하고 오류 근거를 보존한 뒤 신뢰 상태 판정 대상으로 넘긴다.

### 3.3 경로 분류기

| 분류 | 필수 근거 |
| --- | --- |
| `NORMAL_COMPLETED` | 승인과 완료 사건, 최종 `SUCCESS / RESERVED / APPLIED / PAID` |
| `EXPIRED_WITHOUT_PAYMENT` | 승인 사건 없이 만료 사건 존재 |
| `EXPIRATION_FIRST` | 스케줄러 만료 결정 뒤 별도 버전의 승인·환불 대기 결정 |
| `PAYMENT_HANDLER_EXPIRED` | 승인·결제 주체 만료·환불 대기가 같은 결정 버전과 묶음 |

완료에 필요한 사건이 아직 도착하지 않은 생명주기는 확정 경로를 만들지 않고 처리 중 상태로 유지한다.

### 3.4 Consumer 트랜잭션

- Poller가 전달한 결정 단위를 하나의 Consumer 트랜잭션에서 적용한다.
- `eventId` 적용 기록을 먼저 유일성 제약으로 확인한다.
- 조회 모델 갱신과 적용 기록을 함께 커밋한다.
- 실패하면 두 변경을 모두 롤백하고 사건을 재조회 대상으로 유지한다.
- 여러 생명주기를 포함한 만료 배치는 생명주기·결정 단위로 나눠 적용한다.

### 3.5 기본 신뢰 상태

| 상태 | Phase 3 판정 |
| --- | --- |
| `PROCESSING` | 새 사건 적용 중, 순번 공백, 원천 대조 전 |
| `CONSISTENT` | 통합 시험의 원천 대조에서 네 상태와 버전 일치 |
| `INCOMPLETE` | 원천 버전까지 필요한 사건이 없음을 대조로 확인 |
| `MISMATCH` | 같은 원천 버전에서 하나 이상의 상태 필드가 다름 |

Phase 3은 재구성 정확성을 검증하기 위한 원천 대조를 구현하거나 시험 도구로 제공한다. 운영자용 대조 실행과 조회 응답 통합은 Phase 5에서 마감한다.

## 4. 구현 순서

1. 정상·만료·경로 A/B의 사건 고정 데이터를 작성한다.
2. 조회 모델의 스키마·인덱스와 `projectionVersion` 규칙을 확정한다.
3. 상태 축별 순수 재구성 단위 시험을 작성한다.
4. 경로 분류 단위 시험을 작성한다.
5. 적용 기록과 조회 모델 트랜잭션을 구현한다.
6. Poller와 Consumer를 연결하고 설정으로 활성화한다.
7. 원천 대조용 비교기를 구현하거나 통합 시험 도구를 작성한다.
8. 정상·만료·경로 A/B·재시도 통합 시험을 실행한다.
9. Phase 2 사건 부하에서 Consumer 처리율·지연·MySQL 비용을 측정한다.

## 5. 시험 계획

### 5.1 재구성 단위 시험

- 각 사건의 네 상태 축 적용
- 변경 전 상태 불일치 거부
- 같은 버전의 `eventOrdinal` 정렬
- 알 수 없는 `schemaVersion` 처리
- 필수 사건 조합 누락과 잘못된 `commitGroupId` 처리
- 같은 입력을 반복 적용한 결과의 결정성

### 5.2 경로 분류 시험

| 시나리오 | 기대 최종 상태 | 기대 경로 |
| --- | --- | --- |
| 정상 결제 | `SUCCESS / RESERVED / APPLIED / PAID` | `NORMAL_COMPLETED` |
| 결제 없는 만료 | `EXPIRED / AVAILABLE` | `EXPIRED_WITHOUT_PAYMENT` |
| 경로 A | `EXPIRED / AVAILABLE / REFUND_PENDING / PAID` | `EXPIRATION_FIRST` |
| 경로 B | 같은 공통 최종 상태 | `PAYMENT_HANDLER_EXPIRED` |

### 5.3 MySQL 통합 시험

- Poller 조회부터 적용 기록·조회 모델 커밋까지 전체 흐름
- Consumer 트랜잭션 실패 시 적용 기록과 조회 모델 모두 롤백
- 같은 사건 재전달에서 상태 변화 0건
- 두 Poller 후보가 같은 사건을 읽는 경합에서 단일 적용
- 원천 네 상태 축과 조회 모델 비교

### 5.4 기존 업무 회귀

- 예약·결제·만료 정합성 시험
- MySQL 경합 테스트
- 멱등 재시도 시험
- 사건 생성과 Consumer 활성화 전후 사용자 응답 계약 비교

## 7. 예상 변화

- 사건 원본에서 예약·좌석·결제 주문·결제 시도의 현재 상태가 자동으로 구성된다.
- 같은 최종 상태의 경로 A/B가 사건 근거로 분류된다.
- Poller와 Consumer가 운영 설정에서 활성화된다.
- 미처리 사건 수는 Consumer 처리에 따라 감소하고 사건 가시화 지연을 측정할 수 있다.
- MySQL에는 조회 모델과 사건 적용 기록의 쓰기 부하가 추가된다.
- 개발자용 최종 조회 API는 아직 제공하지 않으며 저장소·시험에서 결과를 검증한다.

## 8. 중단·되돌리기 조건

- 기준 시나리오의 상태 일치율 또는 경로 판정 정확도가 100%가 아니다.
- 같은 사건 재전달에서 중복 적용이 발생한다.
- Consumer 실패가 부분 상태를 남긴다.
- 조회 모델 쓰기가 업무 원장 트랜잭션을 예상 범위 이상으로 경합시킨다.
- 사건 계약 위반을 정상 상태로 적용하는 경로가 발견된다.

중단 시 Consumer와 Poller를 비활성화하고 사건 생성과 원본 보존은 유지할 수 있다. 조회 모델은 재생 가능한 파생 데이터로 관리하며 삭제·재생이 필요하면 명시적 작업과 검증을 사용한다.

## 9. 완료 조건

- 정상·만료·경로 A/B의 최종 상태 일치율 100%를 확인한다.
- 경로 A/B 판정 정확도 100%를 확인한다.
- 동일 사건 반복 전달의 중복 적용 0건을 확인한다.
- 적용 기록과 조회 모델의 원자적 커밋·롤백을 확인한다.
- 원천 대조 기준 데이터에서 네 신뢰 상태를 정확히 분류한다.
- 사건 가시화 지연과 Consumer 처리 비용의 기준선을 기록한다.
- [Phase 3 결과](result.md)에 실제 변경·시험·판정을 기록한다.
