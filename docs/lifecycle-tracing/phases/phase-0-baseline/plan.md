## 1. 왜 수행하는가

생명주기 추적 기능을 추가하기 전에 현재 진단 비용, 실행 경로 판정 가능 범위와 예상 사건량을 고정한다. 이후 Phase의 개선 효과와 부하 영향을 같은 질문과 조건으로 비교하기 위한 출발점이다.

현재 기준 질문은 `paymentOrderId` 하나에서 시작해 승인된 결제가 `EXPIRED` 예약과 `REFUND_PENDING` 주문으로 끝난 이유를 설명하는 것이다. 현재 구현은 최종 상태를 저장하며, 상태를 만든 커밋 결정과 실행 경로는 한 결과로 연결하지 않는다.

## 3. 이번 Phase에서 바꿀 것

### 3.1 문서

- 현재 상태와 로그에서 원인을 조사하는 고정 절차를 작성한다.
- 테이블·조회·로그 검색·식별자·진단 단계의 집계 규칙을 고정한다.
- 경로 A와 경로 B의 현재 코드 근거와 판정 한계를 기록한다.
- MVP 요구사항, 제외 범위, 정확성 기준과 Phase 경계를 확정한다.
- 정상·만료·경로 A/B의 예상 사건 수와 업무 처리량에 따른 사건 발생률을 산출한다.

### 3.2 시험과 측정

- MySQL 행 잠금 경합 테스트로 만료 커밋 선행 경로를 재현한다.
- 테스트 데이터를 보존한 상태에서 Q1~Q5 조회와 L1~L4 로그 검색을 실행한다.
- 실제 업무 부하 결과의 성공 상태 전이 수를 사건 계약에 대입해 정상·최대 예상 사건률을 계산한다.
- 사람의 진단 시간 측정 절차를 작성하고 향후 독립 진단자 시험 조건을 고정한다.

### 3.3 애플리케이션 코드와 스키마

Phase 0에서는 애플리케이션·스키마·부하 시험 코드의 기능을 변경하지 않는다. 재현을 막는 안전한 실행 환경 문제만 국소적으로 해결하고, 변경 여부와 영향을 결과에 기록한다.

## 4. 수행 방법

### 단계 1. 대상 시나리오 고정

1. 만료 기준 시각이 지난 예약과 준비된 결제 주문·시도를 만든다.
2. 만료 트랜잭션이 예약·좌석 상태를 변경한 뒤 커밋을 지연한다.
3. 별도 스레드에서 결제 결과 반영을 시작하고 MySQL 잠금 대기를 확인한다.
4. 만료 커밋 뒤 결제 결과 반영을 완료한다.
5. 네 상태 축과 승인 거래 식별자 보존을 검증한다.

### 단계 2. 현재 진단 비용 측정

- 최초 입력은 `paymentOrderId` 하나로 제한한다.
- DB 조회 1회, 로그 검색 1회와 진단 단계의 집계 규칙을 먼저 고정한다.
- 같은 최종 상태의 원인 설명과 실제 실행 순서 확정을 별도로 판정한다.
- 실행 환경 준비 시간과 사람의 진단 시간을 분리한다.

### 단계 3. 사건량 산출

| 경로 | 한 생명주기당 예상 사건 |
| --- | ---: |
| 정상 결제 | 4개 |
| 결제 없는 예약 만료 | 2개 |
| 만료 후 승인 경로 A/B | 5개 |

실제 사건 테이블이 생기기 전에는 성공한 업무 상태 전이 건수에 위 계약을 적용한다. 요청률, 성공률, 만료 처리 건수와 한 생명주기당 사건 수를 함께 기록한다.

### 단계 4. 기준 문서 확정

- 요구사항 ID와 인수 시나리오를 확정한다.
- 현재 측정값과 구현 뒤 목표를 SLI·SLO 문서에서 분리한다.
- 품질속성 우선순위와 Phase별 품질 게이트를 연결한다.

## 6. 예상 변화

- 이후 Phase가 답해야 할 기준 질문과 현재 조사 비용이 고정된다.
- 경로 A/B 판정에 필요한 사건 필드와 신뢰 상태 요구가 명확해진다.
- 500 events/s 지속 처리, 만료 사건 5,000개와 재처리 30,000개의 기술 검증 경계를 평가할 근거가 생긴다.
- 애플리케이션 실행 동작과 데이터 구조는 유지된다.

## 8. 완료 조건

- 현재 진단 절차와 비용이 재현 가능한 형태로 기록된다.
- 경로 A/B의 공통 최종 상태와 현재 판정 가능 범위가 기록된다.
- MVP 기능·제외 범위·인수 시나리오가 확정된다.
- 실제 업무 상태 전이 결과를 근거로 정상·최대 예상 사건량을 산출한다.
- Phase 1 기술 비교에 필요한 정확성·성능·운영 기준이 연결된다.

## 9. 중단 조건

- 기준 시나리오가 현재 코드에서 재현되지 않는다.
- 최종 상태나 잠금 순서가 기존 정합성 시험과 다르다.
- 사건량 산출에 필요한 성공 상태 전이 수를 확보할 수 없다.

중단 시 원인과 필요한 추가 측정을 결과 문서에 기록하고 Phase 1의 처리량 전제를 확정값으로 사용하지 않는다.
