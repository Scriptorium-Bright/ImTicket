## 2. 실제로 수행한 작업

### 2.1 현재 조사 절차 고정

- `paymentOrderId` 하나에서 시작하는 Q1~Q5 DB 조회를 실행했다.
- 주문·예약·결제 시도·예약 좌석 연결·좌석 상태를 확인했다.
- L1~L4 로그 검색의 범위와 집계 규칙을 고정했다.
- 결제 반영 코드, 만료 처리 코드와 MySQL 경합 테스트를 연결해 원인 설명 절차를 12단계로 정리했다.

### 2.2 기준 문서 분리

- 기능 범위와 인수 조건을 요구사항 ID `FR-001`~`FR-014`로 정리했다.
- 정확성 SLO, 성능 측정 항목과 Phase별 품질 게이트를 분리했다.
- 품질속성 시나리오 `QA-01`~`QA-11`을 작성했다.
- Phase 0~5의 진행 전 계획과 실행 후 결과 문서 구조를 만들었다.

### 2.3 코드와 스키마 변경

애플리케이션 코드, 데이터베이스 스키마와 부하 시험 코드는 변경하지 않았다.

## 5. 실행 중 실패와 수정

첫 실행에서 Docker 데이터 영역 사용률이 100%에 도달해 MySQL이 `OS errno 28 - No space left on device`로 시작하지 못했다. 해당 일회용 Testcontainers MySQL의 `/var/lib/mysql`만 `tmpfs`로 지정하고 같은 테스트를 재실행했다. 애플리케이션·시험 소스와 기존 MySQL 데이터는 변경하지 않았다.

## 6. 사건량 산출 상태

| 경로 | 설계 전제 |
| --- | ---: |
| 정상 결제 | 생명주기당 4개 사건 |
| 결제 없는 예약 만료 | 생명주기당 2개 사건 |
| 만료 후 승인 경로 A/B | 생명주기당 5개 사건 |
| 결제 단계별 신규 처리 10건/s 가정 | 정상 흐름 약 40 events/s, 만료 후 승인 흐름 최대 약 50 events/s |
| 만료 최대 배치 | 한 커밋에서 5,000개 사건, 30초 구간 평균 약 167 events/s |

위 수치는 현재 부하 스크립트 기본 입력률과 만료 배치 설정을 결합한 설계 전제다. 실제 성공 트랜잭션 수를 이용한 측정값은 후속 Phase 0 작업에서 확정한다.

## 8. 판정과 다음 작업

현재 진단 기준선과 요구사항은 Phase 1 기술 선택의 입력으로 사용할 수 있다. 실제 사건량은 Phase 2 성능 시험의 Poller 간격·배치 크기를 확정하기 전에 측정한다.
