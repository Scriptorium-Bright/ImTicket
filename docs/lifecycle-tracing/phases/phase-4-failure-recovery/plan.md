# Phase 4 계획: 실패 조건 처리와 재처리

작성일: 2026-09-20(KST)  
상태: 부분 완료  
상위 계획: [구현 계획 7절](../../implementation-plan.md#phase-4-스트리밍-실패-조건-처리)  
실행 결과: [Phase 4 결과](result.md)

## 1. 왜 수행하는가

사건은 중복 전달될 수 있고 결정 순서와 다른 순서로 발견될 수 있다. 처리기는 적용 전·도중·커밋 직후에 종료될 수 있다. Phase 4는 이러한 조건에서 누락과 중복 적용 없이 같은 최종 상태로 수렴하는지 검증하고, 보존 사건에서 조회 모델을 다시 만드는 재처리 기능을 완성한다.

장애 복구는 메모리 상태에 의존하지 않는다. MySQL의 사건 원본, 사건 적용 기록과 원자적 Consumer 트랜잭션을 복구 근거로 사용한다.

## 2. 시작 조건

- Phase 3의 정상·만료·경로 A/B 상태 일치율과 경로 판정 정확도가 100%다.
- 사건 적용 기록과 조회 모델 변경이 하나의 Consumer 트랜잭션으로 동작한다.
- 같은 사건 재전달의 중복 적용이 0건이다.
- 사건 가시화 지연, Consumer 처리 시간과 정상 처리 대기량 기준선이 있다.
- 시험 전용 장애 주입 지점이 제품 코드의 정상 경로와 분리돼 있다.

## 3. 변경 범위

### 3.1 순서 역전과 지연 처리

- 기대 버전보다 높은 `decisionVersion`을 받으면 적용을 보류한다.
- 원본 사건에 빠진 버전이 있는지 다시 조회한다.
- 공백이 해소되면 마지막 연속 버전부터 정렬해 적용한다.
- 아직 처리 가능한 사건이 남아 있으면 `PROCESSING`을 유지한다.
- 원천 대조에서 사건 부재가 확정되면 `INCOMPLETE`와 공백 범위를 기록한다.
- 지연 사건이 도착하면 자동으로 재평가하고 기준 결과로 수렴한다.

### 3.2 재시도와 오류 상태

| 항목 | 계획 |
| --- | --- |
| 재시도 단위 | `(lifecycleId, decisionVersion)` |
| 재시도 근거 | 미적용 사건과 마지막 처리 오류 |
| 오류 기록 | 실패 시각, 오류 분류, 시도 횟수, 다음 처리 가능 시각 |
| 일시 오류 | 제한된 지수 백오프 또는 설정된 재시도 간격으로 재처리 |
| 계약·데이터 오류 | 자동 반복을 제한하고 운영 확인 대상으로 표시 |
| 성공 뒤 | 오류 상태 정리, 적용 기록과 조회 모델 커밋 |

재시도 횟수와 간격은 시험에서 처리 대기량과 복구 시간을 측정한 뒤 확정한다. 계약 오류를 무한 반복하지 않도록 분류와 운영 지표를 제공한다.

### 3.3 재처리 기능

- 입력은 사건 원본 범위와 목표 `projectionVersion`이다.
- 목표 조회 모델은 비어 있거나 재처리 전용 버전으로 격리한다.
- 사건은 `lifecycleId`, `decisionVersion`, `eventOrdinal` 순서로 적용한다.
- 재처리 중 기존 운영 조회 모델을 변경하지 않는다.
- 완료 후 기존 결과와 네 상태 축, Timeline, 경로와 신뢰 상태를 비교한다.
- 비교 결과를 확인한 뒤 조회 버전 전환 여부를 별도 결정한다.

재처리 명령은 동일 실행의 중복 시작을 막고, 실행 ID·범위·시작·종료·처리 수·오류 수를 기록한다.

### 3.4 관측과 운영 정보

| 지표 | 목적 |
| --- | --- |
| 재전달 중복 사건 수 | 멱등 처리 입력 규모 확인 |
| 순번 공백 생명주기 수 | 지연·누락 후보 확인 |
| 재시도 수와 오류 분류 | 일시 오류와 계약 오류 분리 |
| 최대 처리 대기량 | 장애 중 누적 규모 확인 |
| 장애 복구 시간 | 재시작 뒤 정상 범위 회복 측정 |
| 재처리 처리율·완료 시간 | 조회 모델 재생 용량 확인 |
| 재처리 결과 차이 수 | 새 결과의 동일성 판정 |

## 5. 구현 순서

1. 장애 주입 매트릭스와 정상 기준 결과를 고정한다.
2. 순번 공백 보류와 재평가 시험을 먼저 작성한다.
3. 재시도 상태·오류 분류·지표를 구현한다.
4. Consumer 종료 지점별 시험 장치를 작성한다.
5. F-01~F-09를 실행하고 누락·중복·부분 상태를 검증한다.
6. 원천 대조의 `INCOMPLETE`·`MISMATCH` 주입 시험을 실행한다.
7. 재처리 서비스와 실행 잠금·실행 기록을 구현한다.
8. 30,000개 사건 재처리와 결과 비교를 실행한다.
9. 장애 복구 시간, 최대 처리 대기량과 재처리 처리율을 3회 이상 측정한다.
10. 재시도 설정과 복구 SLO 후보를 확정한다.

## 8. 예상 변화

- Poller·Consumer 재시작과 중복 전달이 조회 모델 정확성에 영향을 주지 않는다.
- 순서가 늦은 사건은 신뢰 상태로 드러나고 도착 후 자동 수렴한다.
- 계약 오류와 원천 누락은 운영 확인이 필요한 상태로 구분된다.
- 보존 사건에서 새 조회 모델 버전을 안전하게 만들고 기존 결과와 비교할 수 있다.
- 재시도 상태·오류 기록·재처리 실행 기록을 위한 저장량과 지표가 추가된다.

## 9. 중단·되돌리기 조건

- 한 건의 누락, 중복 적용 또는 부분 커밋이 발생한다.
- 재처리가 기존 결과와 다른데 원인을 설명할 수 없다.
- 계약 오류가 정상 처리 대기량을 지속적으로 막는다.
- 재시도 폭증으로 MySQL 또는 업무 API의 기존 SLO가 악화된다.
- 30,000개 재처리에서 정확성 SLO를 유지하지 못한다.

중단 시 자동 재시도 또는 Poller를 비활성화하고 사건 원본을 보존한다. 조회 모델 버전 전환은 수행하지 않으며, 기존 검증된 버전을 계속 사용한다.

## 10. 현재 실행 범위와 완료 조건

이번 실행에서 완료한 범위는 F-01~F-04, F-06, F-09~F-12다. F-12는 H2 `@DataJpaTest`에서 7,500개 Lifecycle에 사건 4건씩 넣어 총 30,000건을 별도 Projection으로 Replay하는 방식으로 측정했다.

- 중복 사건은 적용 기록으로 한 번만 반영한다.
- 순서 역전·지연 사건은 `PENDING`과 `PROCESSING`을 거쳐 연속 버전에 수렴한다.
- 계약 오류는 상태를 변경하지 않고 `FAILED`, `CONTRACT`, 시도 횟수와 오류 코드를 기록한다.
- 적용 트랜잭션 롤백 뒤 같은 사건을 다시 읽어 Snapshot을 처음부터 적용한다.
- 원천 대조가 `CONSISTENT`, `INCOMPLETE`, `MISMATCH`를 구분하고 차이를 저장한다.
- Replay은 사용하지 않은 `projectionVersion`에 사건을 다시 적용하고 실행 결과를 기록한다.
- F-05·F-07의 실제 프로세스 종료와 F-08의 MySQL 연결 장애 주입은 별도 실행 조건으로 남긴다.
- 실제 실행 결과와 미실행 항목을 [Phase 4 결과](result.md)에 기록한다.
