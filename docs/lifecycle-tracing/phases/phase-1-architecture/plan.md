# Phase 1 계획: 사건 모델과 기술 선택

작성일: 2026-09-20(KST)  
상태: 완료  
상위 계획: [구현 계획 7절](../../implementation-plan.md#phase-1-사건-모델과-기술-선택)  
실행 결과: [Phase 1 결과](result.md)

## 1. 왜 수행하는가

Phase 2 구현 전에 커밋된 업무 사실을 생성하는 위치, 생명주기 순서, 중복 제거, 장애 재개와 재처리 책임을 확정한다. 현재 규모에서 요구사항을 충족하는 가장 단순한 실행 구성을 선택하고, 처리량이나 기능 요구가 커질 때의 기술 재검토 조건도 함께 고정한다.

## 2. 시작 조건

- Phase 0의 현재 진단 기준선과 경로 A/B 코드 근거가 있다.
- MVP 기능 `FR-001`~`FR-014`와 여섯 사건 종류가 정의돼 있다.
- 업무 상태 변경은 Spring과 JPA가 관리하는 MySQL 트랜잭션에서 수행된다.
- 결제 준비, 결제 반영과 만료 처리는 같은 예약 행의 쓰기 잠금을 사용한다.
- 현재 저장소에는 Kafka, Kafka Connect, Debezium과 Flink 실행 구성이 없다.

실제 업무 실행 기반 사건량은 Phase 0의 남은 측정 항목이다. Phase 1에서는 부하 스크립트와 만료 배치 설정에서 도출한 설계 전제를 사용하고, 실제 측정이 달라지면 Poller 설정과 기술 재검토 조건을 갱신한다.

## 3. 결정할 질문

1. 커밋된 업무 사건을 어느 트랜잭션 경계에서 생성하는가?
2. 업무 상태와 사건 기록의 원자성을 어떻게 보장하는가?
3. 같은 생명주기의 커밋 결정 순서를 어떤 값으로 재현하는가?
4. 같은 결정 안의 여러 사건과 여러 예약을 포함한 만료 배치를 어떻게 구분하는가?
5. 동일 사건을 반복 전달해도 한 번만 적용하는 방법은 무엇인가?
6. 처리기가 중단됐을 때 어느 데이터에서 다시 시작하는가?
7. 조회 모델을 새 버전으로 재처리할 원본은 무엇인가?
8. 현재 구성에서 운영해야 할 배포 단위와 지표는 무엇인가?
9. Kafka·Debezium·Flink를 다시 비교할 측정 조건은 무엇인가?

## 4. 비교 대상

### 4.1 사건 생성 위치

- 애플리케이션 직접 메시지 발행
- 트랜잭션 아웃박스
- 도메인 테이블 변경 데이터 캡처(Change Data Capture, CDC)
- 트랜잭션 아웃박스와 CDC 전달 결합

평가 기준은 커밋 원자성, 업무 의미 보존, 순서·중복 처리, 장애 복구·재처리와 운영 복잡도다.

### 4.2 전달 방식

- MySQL 폴링
- Kafka 기반 내구성 있는 메시징
- 프로세스 내부 큐

평가 기준은 예상 사건량 처리 여유, 장애 재개 위치, 사건 보존, 독립 Consumer 요구와 운영 책임이다.

### 4.3 생명주기 처리 방식

- 멱등 단순 Consumer
- 상태 저장 스트림 처리
- 주기 배치 재구성

평가 기준은 여섯 사건의 결정적 재구성, 지연·역전 처리, 체크포인트, 배포와 운영 비용이다.

### 4.4 저장소

- 기존 MySQL의 사건 원본과 조회 모델
- 별도 사건 저장소 또는 스트림 처리 상태 저장소

평가 기준은 원천 대조, 적용 원자성, 한 건 조회, 재처리와 저장 부하다.

## 5. 바꿀 문서와 설계

| 대상 | 변경 내용 |
| --- | --- |
| 요구사항 | 사건 계약, 조회 결과, 인수 시나리오 확정 |
| ADR | 선택 기술, 제외·보류 후보, 재검토 조건 기록 |
| C4 | 컨테이너·컴포넌트·트랜잭션·배포 경계 작성 |
| SLI·SLO | 정확성 고정 목표와 측정 후 확정할 성능 목표 분리 |
| 품질속성 | 원자성·복구·성능·보안·변경 시나리오 작성 |
| 구현 계획 | Phase 2~5의 산출물과 품질 게이트 연결 |

Phase 1에서는 애플리케이션 코드와 데이터베이스 스키마를 변경하지 않는다.

## 6. 설계 검증 방법

| 검증 질문 | 사용할 예제 | 통과 조건 |
| --- | --- | --- |
| 원자성 | 정상 커밋과 롤백 | 상태와 사건이 함께 커밋·롤백되는 설계 |
| 순서 | 정상, 경로 A, 경로 B | 재처리해도 같은 결정 순서와 경로 생성 |
| 중복 | 같은 `eventId` 반복 전달 | 조회 모델의 단일 적용 가능 |
| 역전·지연 | 높은 버전 선도착 | 보류 상태와 공백 해소 규칙 존재 |
| 장애 재개 | 적용 전·도중·커밋 직후 종료 | 내구성 있는 원본과 적용 기록에서 재개 가능 |
| 재처리 | 빈 조회 모델 버전 | 같은 사건에서 상태·Timeline·경로 재생 가능 |
| 운영 적합성 | 현재 Java·Spring·MySQL 구성 | 추가 플랫폼 없이 초기 배포 가능 |

## 7. 예상 변화

- Phase 2에서 구현할 스키마와 컴포넌트 책임이 확정된다.
- 생명주기 순서가 서버 시각과 전달 순서에 의존하지 않게 된다.
- Kafka·Debezium·Flink 도입은 측정된 처리량과 기능 요구로 판단하게 된다.
- 사건 원본, 조회 모델과 원천 대조의 책임이 분리된다.
- 초기 운영 구성은 기존 Spring Boot와 MySQL 안에서 유지된다.

## 9. 완료 조건

- 여섯 사건의 필수 필드와 경로 A/B 표현을 확정한다.
- 생산·전달·처리·저장·조회·재처리의 기술과 버전을 확정한다.
- `sourceOrder`, 중복 제거, 순번 공백과 장애 재개 규칙을 확정한다.
- C4에서 컨테이너·컴포넌트·데이터·배포 경계를 표현한다.
- 정확성 SLO와 성능 측정 기준을 확정한다.
- Kafka·Debezium·Flink 재검토 조건을 기록한다.

## 10. 중단 조건

- 업무 상태와 사건을 같은 트랜잭션에 기록할 수 없다.
- 예약 행 잠금 규칙으로 생명주기 결정 순서를 보장할 수 없다.
- 설계 전제의 사건량이 MySQL 폴링 검증 경계를 이미 초과한다.
- 독립 배포 Consumer 또는 서비스 간 전달이 초기 필수 요구로 확인된다.

중단 조건이 발생하면 사건 생성 위치 또는 전달 방식을 다시 비교하고 ADR에 결정 상태를 기록한다.
