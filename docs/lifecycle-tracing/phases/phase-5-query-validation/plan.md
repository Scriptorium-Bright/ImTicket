# Phase 5 계획: 조회 및 최종 검증

작성일: 2026-09-20(KST)  
상태: 미실행  
상위 계획: [구현 계획 7절](../../implementation-plan.md#phase-5-조회-및-최종-검증)  
실행 결과: [Phase 5 결과](result.md)

## 1. 왜 수행하는가

생명주기 사건과 조회 모델이 정확해도 사용자가 여러 테이블과 로그를 직접 확인해야 하면 기준 질문을 해결하지 못한다. Phase 5는 `paymentOrderId` 또는 `reservationId` 하나로 네 상태 축, 사건, 실행 경로, 신뢰 상태와 원천 차이를 조회하게 하고, Phase 0의 진단 기준선을 같은 질문으로 다시 측정한다.

이 Phase는 기능 정확성, 장애 복구, 조회 계약, 접근 통제, 성능과 진단 효율을 한 번에 확인하는 최종 인수 단계다.

## 2. 시작 조건

- Phase 2~4의 정확성 SLO가 모두 통과했다.
- 정상·만료·경로 A/B, 중복·역전·지연·재시작·재처리의 고정 시험 데이터가 있다.
- 복구 시간, 사건 가시화 지연과 처리 대기량 기준선이 있다.
- 조회 모델의 `paymentOrderId`·`reservationId` 인덱스가 준비돼 있다.
- 조회 API의 사용자 역할, 접근 경로와 데이터 보존 범위를 구현 전에 승인한다.

## 3. 변경 범위

### 3.1 조회 API 또는 최소 조회 도구

입력은 다음 두 방식 중 하나다.

- `paymentOrderId` 하나
- `reservationId` 하나

두 식별자를 동시에 받거나 둘 다 비어 있는 요청은 검증 오류로 처리한다. 정확한 HTTP 경로와 오류 응답은 구현 전 `query-api-contract.md`로 분리할 수 있다.

응답은 다음 정보를 포함한다.

```text
LifecycleView
├── lifecycleId / reservationId / paymentOrderId
├── Reservation 현재 상태
├── Seat 현재 상태 목록
├── PaymentOrder 현재 상태
├── PaymentAttempt 현재 상태 목록
├── decisionVersion 순서의 사건 목록
├── pathClassification과 판정 근거
├── trustStatus
├── 마지막 원천 대조 시각
└── 원천 버전·조회 버전과 필드 차이 목록
```

`paymentOrderId`와 `reservationId` 조회는 같은 `lifecycleId`와 같은 응답 내용을 반환해야 한다.

### 3.2 원천 대조 기능

- 식별자 하나로 Reservation, 모든 연결 Seat, PaymentOrder와 모든 PaymentAttempt를 읽는다.
- 원천 `lifecycleVersion`, 조회 모델 버전과 사건의 최대 연속 버전을 비교한다.
- 상태 필드를 Entity·식별자 단위로 비교한다.
- `CONSISTENT`, `PROCESSING`, `INCOMPLETE`, `MISMATCH`와 판정 근거를 저장한다.
- 대조 기능은 차이를 자동 수정하지 않는다.
- 대량 전체 대조는 MVP 범위에서 제외하고 한 건 또는 제한된 배치로 시작한다.

### 3.3 접근 통제와 데이터 최소화

- 생명주기 조회와 원천 대조·재처리는 일반 사용자 공개 API로 노출하지 않는다.
- 기존 Spring Security 정책에 운영 조회 권한을 명시한다.
- 미인증·미인가 요청을 차단하고 보안 시험을 추가한다.
- 카드 정보, JWT·세션 토큰, 결제대행사 비밀 값과 원본 요청 본문을 저장·반환하지 않는다.
- 원천 대조와 재처리 실행 주체·범위·결과를 감사 가능한 형태로 기록한다.
- 식별자는 Micrometer 태그로 사용하지 않는다.

운영 조회 역할이 현재 권한 모델에 없으면 구현 전에 권한 설계와 영향 범위를 별도 결정 문서로 확정한다.

### 3.4 오류 계약

| 조건 | 응답 원칙 |
| --- | --- |
| 잘못된 식별자 형식 | 검증 오류와 허용 형식 제공 |
| 생명주기 없음 | 존재하지 않음을 명시하는 응답 |
| 처리 중 | 현재 조회 결과와 `PROCESSING`, 마지막 적용 버전 제공 |
| 사건 누락 | `INCOMPLETE`, 공백 버전과 대조 근거 제공 |
| 원천 불일치 | `MISMATCH`, 필드별 차이 제공 |
| 내부 조회 실패 | 상관관계 식별자와 안정된 오류 계약 제공, 민감정보 제외 |

정확한 HTTP 상태와 응답 스키마는 API 계약 시험과 함께 확정한다.

### 3.5 관측과 운영 문서

| 항목 | 변경 |
| --- | --- |
| 조회 지표 | 성공·없음·처리 중·불일치 결과 수, 조회 지연 |
| 원천 대조 지표 | 신뢰 상태별 결과 수와 실행 시간 |
| 보안 지표 | 미인가 요청 수, 운영 작업 결과 수 |
| 운영 절차 | 식별자 조회, 불일치 해석, 재처리 실행·비교, 에스컬레이션 순서 |
| 대시보드 | 사건 지연·처리 대기량·신뢰 상태·조회 지연을 함께 확인 |

## 4. 구현 순서

1. 조회 사용자·권한·API 오류 계약을 승인한다.
2. `paymentOrderId`와 `reservationId` 조회 저장소 시험을 작성한다.
3. LifecycleView 조립과 Timeline 정렬 시험을 작성한다.
4. 보호된 조회 API 또는 최소 조회 도구를 구현한다.
5. 원천 대조 기능과 필드 차이 응답을 구현한다.
6. 조회·대조·보안 지표와 구조화 로그를 추가한다.
7. 정상·만료·경로 A/B 조회 인수 시험을 실행한다.
8. Phase 4의 실패 조건 전체를 조회 결과에서 재검증한다.
9. 조회 부하 시험으로 지연·SQL 수·MySQL 자원 사용량을 측정한다.
10. Phase 0 기준 질문으로 진단 절차와 사람의 원인 확인 시간을 다시 측정한다.
11. 결과를 SLI·SLO, C4, 운영 절차와 최종 결과 문서에 반영한다.

## 6. Phase 0 기준선 재측정

같은 질문과 종료 조건을 사용한다.

> 이 결제는 승인되었는데 왜 예약은 `EXPIRED`이고 `PaymentOrder`는 `REFUND_PENDING`인가?

| SLI | Phase 0 | Phase 5 기록 |
| --- | ---: | --- |
| 확인 Entity/Table | 5개 | 생명주기 조회 밖에서 직접 확인한 수 |
| DB 조회 | 5회 | 추가 원천 조회 수 |
| 기본 로그 검색 | 4회 | 추가 검색 수 |
| 업무 식별자 | 6종 | 사용자가 입력한 식별자 종류 수 |
| 진단 단계 | 12단계 | 입력부터 원인·경로 확인까지 단계 수 |
| 생명주기 조회 | 기능 없음 | 1회 |
| 경로 A/B 판정 | 개별 운영 건 근거 부족 | 제어된 A/B 판정 정확도 |
| 사람의 원인 확인 시간 | 측정 전 | 독립 진단자 3회 이상의 중앙값·범위 |

진단자는 정답을 미리 보지 않고 식별자와 접근 환경만 받는다. 환경 준비 시간과 진단 시간을 분리하고, 상태 원인 설명 시각과 실행 경로 확정 시각을 따로 기록한다.

## 8. 예상 변화

- 운영자와 개발자는 식별자 하나로 상태, 사건, 경로와 데이터 신뢰 상태를 확인한다.
- 경로 A/B 원인 설명에 추가 코드 해석과 로그 검색이 필요하지 않게 된다.
- 사건 누락과 상태 불일치가 명시적인 신뢰 상태와 필드 차이로 드러난다.
- 조회·원천 대조의 HTTP·SQL 부하와 보안 운영 책임이 추가된다.
- Phase 0의 진단 비용을 같은 조건으로 비교할 수 있다.

## 9. 중단·되돌리기 조건

- 조회 결과가 원천 상태 또는 사건 Timeline과 다르다.
- `paymentOrderId`와 `reservationId`가 서로 다른 생명주기를 반환한다.
- 미인가 사용자가 조회·대조·재처리를 실행할 수 있다.
- 응답이나 로그에 민감정보가 포함된다.
- 조회 부하가 MySQL 업무 원장의 기존 SLO를 지속적으로 악화시킨다.

중단 시 조회 API를 비활성화하고 사건 생성·처리·조회 모델은 유지한다. 잘못된 조회 모델은 검증된 버전으로 전환하거나 보존 사건에서 새 버전을 재생한다.

## 10. 완료 조건

- V-01~V-12 인수 시험을 모두 통과한다.
- 식별자 하나의 조회 1회로 네 상태 축, 사건, 경로와 신뢰 상태를 확인한다.
- 경로 A/B 판정 정확도와 조회 결과 완전성이 100%다.
- 미인가 접근 차단과 데이터 최소화 기준을 통과한다.
- 조회 지연·SQL 수·MySQL 자원 기준선을 기록하고 SLO를 확정한다.
- Phase 0 진단 지표와 사람의 원인 확인 시간을 재측정한다.
- 운영 절차와 대시보드에 불일치·재처리 대응을 연결한다.
- [Phase 5 결과](result.md)에 최종 변경·시험·판정을 기록한다.
