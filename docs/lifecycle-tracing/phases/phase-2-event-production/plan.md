# Phase 2 계획: 사건 생성과 수집

작성일: 2026-09-20(KST)  
상태: 부분 완료  
상위 계획: [구현 계획 7절](../../implementation-plan.md#phase-2-사건-생성과-수집)  
실행 결과: [Phase 2 결과](result.md)

## 1. 왜 수행하는가

현재 업무 원장은 최종 상태를 저장하며, 상태를 만든 결정 사유·주체·커밋 묶음과 순서를 보존하지 않는다. Phase 2는 예약·결제 상태 변경과 같은 트랜잭션에 생명주기 사건을 기록하고, 미처리 사건을 지속적으로 발견할 수 있는 내구성 있는 입력 경계를 만든다.

이 Phase가 끝나면 정상 커밋의 사건은 반드시 존재하고, 롤백된 상태 변경의 사건은 존재하지 않아야 한다. 조회 모델과 경로 분류는 Phase 3에서 구현한다.

## 2. 시작 조건

- [요구사항](../../requirements.md)의 FR-001~FR-005와 사건 계약이 승인돼 있다.
- [ADR-001](../../phase-1-technology-adr.md)의 트랜잭션 아웃박스·MySQL 폴링 결정이 승인돼 있다.
- 실제 업무 상태 전이 기반 사건량을 측정하고 Poller 간격·배치 크기의 초기값에 반영한다.
- 대상 업무 서비스의 트랜잭션과 Reservation 쓰기 잠금 경로를 다시 확인한다.
- 적용 전 예약·결제 API 지연, 만료 처리 시간과 MySQL 잠금 대기 기준선을 확보한다.

## 3. 변경 범위

### 3.1 데이터베이스 스키마

| 대상 | 계획 변경 | 이유 |
| --- | --- | --- |
| `Reservation` | `lifecycle_version` 추가, 생성 시 1 또는 명시된 초기값 사용 | 예약 단위 커밋 결정 순서 보존 |
| `lifecycle_event` | 사건 원본 테이블 생성 | 커밋된 업무 사건의 내구성 있는 원본 |
| 유일성 제약 | `event_id`, `(lifecycle_id, decision_version, event_ordinal)` | 중복 사건과 순번 충돌 차단 |
| 조회 인덱스 | 미처리 조회, `lifecycle_id`, `payment_order_id`, `commit_group_id` | Poller와 단일 식별자 조회 지원 |
| 처리 메타데이터 | 사건 업무 필드와 분리된 전달·시도 상태 | 사건 원본의 불변성 유지 |

`lifecycle_event`의 구조화 열과 `seatIds`, `stateChanges`, `reasonCode` payload, 정확한 자료형, 외래 키와 인덱스는 [데이터 모델과 ERD](../../data-model-erd.md)를 따른다.

마이그레이션은 추가 방식으로 작성한다. 기존 업무 열과 데이터를 삭제하거나 변환하지 않는다.

### 3.2 사건 계약 코드

다음 책임을 분리한다.

| 책임 | 계획 구성 요소 |
| --- | --- |
| 사건 식별과 공통 필드 | `LifecycleEvent` 계약과 `schemaVersion`별 payload |
| 상태 변경 표현 | Entity별 `StateChange` |
| 결정 순서 | `decisionVersion`, `eventOrdinal`, `commitGroupId` 생성 규칙 |
| 업무 사건 조립 | 사건 종류별 Factory 또는 명시적 생성 메서드 |
| 저장 | `LifecycleEventWriter`와 저장소 |
| 직렬화 | Jackson 기반 payload 직렬화·역직렬화 |

패키지 위치는 기존 `reservation.booking`과 `payment`의 의존 방향을 확인한 뒤 공통 생명주기 모듈로 확정한다. 도메인 서비스가 Poller나 조회 모델 구현에 의존하지 않도록 사건 기록 인터페이스만 호출한다.

### 3.3 업무 서비스

| 업무 경로 | 계획 사건 | 핵심 검증 |
| --- | --- | --- |
| 예약 생성·좌석 선점 | `ReservationCreated` | 예약·좌석 상태와 같은 커밋 |
| 결제 준비 | `PaymentPrepared` | 주문·시도 생성과 같은 커밋 |
| 정상 승인 반영 | `PaymentApproved`, `ReservationCompleted` | 같은 결정 버전과 커밋 묶음 |
| 스케줄러 만료 | `ReservationExpired(actor=EXPIRATION_SCHEDULER)` | 예약별 결정 버전, 대량 배치에서도 생명주기별 순서 보존 |
| 결제 반영 중 만료 | `PaymentApproved`, `ReservationExpired(actor=PAYMENT_VERIFICATION)`, `PaymentRefundPending` | 세 사건의 같은 버전·커밋 묶음 |

멱등 재응답, 상태 변화가 없는 재시도와 중복 스케줄러 후보는 새 업무 사건을 만들지 않는다.

### 3.4 Poller 기반 수집 경계

- Spring `@Scheduled`와 ShedLock으로 초기 Poller 하나를 실행한다.
- 미처리 사건을 `(lifecycleId, decisionVersion)` 결정 단위로 읽는다.
- 한 결정의 사건 전체를 함께 읽어 배치 경계가 커밋 묶음을 나누지 않게 한다.
- 아웃박스 기본 키 최댓값을 전역 체크포인트로 사용하지 않는다.
- Phase 2에서는 Poller 조회·묶음·재시도 경계를 검증한다.
- 운영 스케줄 활성화와 적용 완료 처리는 Phase 3 Consumer가 준비된 뒤 함께 켠다.

### 3.5 설정과 관측

| 항목 | 계획 |
| --- | --- |
| 기능 활성화 | 사건 생성과 Poller 활성화를 분리한 설정 |
| Poller 간격·배치 | 실제 사건량과 500 events/s 검증 결과로 결정 |
| 지표 | 커밋 사건 수, Poller 조회 수, 미처리 사건 수, 직렬화 실패, 저장 실패, Poller 실행 시간 |
| 로그 | `eventId`·`lifecycleId`를 전체 로그에 반복 출력하지 않고 실패 원인과 집계 중심으로 기록 |

## 4. 구현 순서

1. 적용 전 성능·잠금 기준선을 같은 시험 조건으로 확보한다.
2. [데이터 모델과 ERD](../../data-model-erd.md)의 물리 스키마, 기존 데이터 전환과 사건 JSON 예제를 검토하고 마이그레이션을 작성한다.
3. 사건 계약·직렬화·유일성 시험을 먼저 작성한다.
4. Reservation 생명주기 버전 증가 규칙과 아키텍처 시험을 작성한다.
5. 예약 생성과 결제 준비 경로에 사건 생성을 적용한다.
6. 결제 완료·만료 경로에 여러 사건의 커밋 묶음을 적용한다.
7. Poller의 결정 단위 조회와 ShedLock 실행 경계를 구현한다.
8. Micrometer 지표와 설정을 추가한다.
9. 정상·롤백·재시도·경합 통합 시험을 실행한다.
10. 지속·버스트 부하를 실행하고 적용 전후 지연·잠금·자원 값을 비교한다.

각 단계에서 실패하면 해당 단계의 원인을 수정하고 그 단계의 시험부터 다시 실행한다.

## 5. 시험 계획

### 5.1 계약·단위 시험

- 여섯 사건의 필수 필드와 `schemaVersion`별 직렬화 왕복
- `stateChanges`의 Entity·식별자·변경 전후 상태 보존
- 같은 결정의 `eventOrdinal` 순서
- 잘못된 빈 식별자, 음수 버전과 중복 순번 거부

### 5.2 MySQL 통합 시험

| 시나리오 | 성공 기준 |
| --- | --- |
| 정상 예약 생성 | 업무 상태와 `ReservationCreated` 함께 커밋 |
| 결제 준비 | 주문·시도와 `PaymentPrepared` 함께 커밋 |
| 정상 결제 완료 | 승인·완료 사건이 같은 결정 규칙을 따름 |
| 경로 A | 만료 사건 버전 뒤 승인·환불 대기 버전 생성 |
| 경로 B | 승인·만료·환불 대기 사건이 같은 버전·묶음 |
| 롤백 | 상태 변경 사건 0건 |
| 멱등 재응답 | 추가 업무 사건 0건 |
| 유일성 충돌 | 트랜잭션 실패와 기존 사건 보존 |
| 동시 상태 변경 | 예약 행 잠금 순서와 단조 증가 버전 유지 |

### 5.3 Poller 시험

- 같은 결정의 사건을 한 묶음으로 반환한다.
- 작은 기본 키가 늦게 커밋되는 경합에서도 사건을 건너뛰지 않는다.
- 여러 애플리케이션 인스턴스 조건에서 ShedLock이 Poller 하나만 실행하게 한다.
- 읽기 또는 처리 실패 뒤 사건이 다시 조회된다.

### 5.4 성능 시험

| 조건 | 측정값 | 판정 |
| --- | --- | --- |
| 기존 예약·결제 부하 | API p50·p95·p99, 트랜잭션 시간, lock wait, MySQL CPU·I/O | 적용 전후 비교와 기존 정합성 유지 |
| 500 events/s 지속 입력 | 처리율, Poller 시간, 미처리 사건 증가량 | 정확성 SLO 유지, 대기량 해소 여부 기록 |
| 만료 사건 5,000개 커밋 | 만료 트랜잭션 시간, 잠금 유지 시간, INSERT 비용 | 실패 0, 변화량 기록 |

성능 목표값은 독립 실행 3회 이상의 중앙값과 범위를 확보한 뒤 SLI·SLO 문서에 확정한다.

## 7. 예상 변화

### 기능

- 각 업무 트랜잭션의 결정 사유·주체·상태 변경과 순서가 MySQL에 남는다.
- 사건 생성 실패는 업무 트랜잭션 실패로 처리된다.
- Poller가 미처리 결정 단위를 지속적으로 발견할 수 있다.
- 사용자 응답 계약과 최종 업무 상태는 유지된다.

### 성능과 운영

- 업무 트랜잭션마다 사건 INSERT와 Reservation 버전 갱신 비용이 추가된다.
- 만료 배치는 처리 예약 수에 비례한 사건 INSERT를 수행한다.
- MySQL 저장량, redo·I/O, 잠금 유지 시간과 Poller 조회 부하가 증가할 수 있다.
- 커밋 사건 수와 미처리 사건 수를 지표로 확인할 수 있다.

## 8. 중단·되돌리기 조건

다음 조건에서는 Phase 3으로 진행하지 않고 원인을 해결한다.

- 정상 커밋 사건 누락 또는 롤백 사건이 한 건이라도 발생한다.
- 기존 정합성 시험이 실패한다.
- `decisionVersion`이 동시 처리에서 단조 증가하지 않는다.
- 만료 배치의 사건 INSERT로 업무 트랜잭션이 시험 제한 시간을 넘거나 잠금 경합이 지속된다.
- 500 events/s 조건에서 Poller 처리 대기량이 계속 증가한다.

되돌리기는 사건 생성·Poller 설정을 비활성화하고 기존 업무 경로를 유지하는 순서로 수행한다. 추가 스키마는 원시 근거 보존과 안전한 배포를 위해 즉시 삭제하지 않는다. 데이터 삭제가 필요하면 별도 승인과 복구 계획을 사용한다.

## 9. 완료 조건

- 여섯 사건의 스키마·계약·생성 위치가 코드와 문서에서 일치한다.
- 정상 커밋 사건 누락 0건, 롤백 사건 0건을 통합 시험으로 확인한다.
- 경로 A/B의 결정 버전과 커밋 묶음이 기대 규칙과 일치한다.
- Poller가 결정 단위로 모든 미처리 사건을 발견한다.
- 기존 정합성 시험을 유지한다.
- 적용 전후 API 지연, 만료 처리 시간, MySQL 잠금·자원 차이를 문서화한다.
- 처리량 검증 결과로 Poller 초기 설정과 기술 재검토 여부를 결정한다.
- [Phase 2 결과](result.md)에 실제 변경·시험·판정을 기록한다.
