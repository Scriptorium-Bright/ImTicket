## 3. 문제에서 설계까지의 흐름

```text
운영 질문을 한 건 단위로 설명하기 어려움
  → baseline.md에서 조사 비용과 A/B 판정 공백 확인
  → requirements.md에서 해결 범위와 사건 계약 고정
  → phase-1-technology-adr.md에서 원자성·순서·복구 요구에 맞는 기술 선택
  → c4-architecture.md에서 실행 구성 요소와 책임 분리
  → data-model-erd.md에서 저장 구조와 기존 데이터 전환 확정
  → lifecycle-reconstruction-spec.md에서 같은 입력이 같은 결과가 되는 규칙 확정
  → SLI·SLO와 품질속성 문서에서 구현 완료 증거 정의
```

문서를 이 순서로 읽으면 “어디서 불편을 확인했고, 왜 이 구조를 선택했으며, 무엇으로 개선을 증명하는가”를 이어서 확인할 수 있다.

## 4. 문서 책임

- 요구사항 변경은 `requirements.md`에 먼저 반영하고 요구사항 식별자를 유지한다.
- 기술 선택 또는 재검토 조건 변경은 ADR에 기록한다.
- 구성 요소와 실행 경계 변경은 C4 문서에 반영한다.
- 테이블, 키, 제약, 인덱스와 데이터 전환 규칙 변경은 데이터 모델·ERD에 반영한다.
- 사건 적용, 경로 판정, 신뢰 상태와 Replay 규칙 변경은 재구성 명세에 반영한다.
- 지표 정의와 목표값 변경은 SLI·SLO 문서에 근거 실행 결과를 연결한다.
- 품질 우선순위와 품질 게이트 변경은 품질속성 문서에 반영한다.
- 실험 절차와 누적 결과는 별도 실행 문서에 기록하고 이 문서들에는 확정된 기준만 남긴다.

## 5. 상태 표기

| 표기 | 의미 |
| --- | --- |
| 현재 | 코드 또는 실행 결과로 확인한 사실 |

| 측정 전 | 지표 정의는 완료됐으며 기준값 수집이 남은 상태 |
