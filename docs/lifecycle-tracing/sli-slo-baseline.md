## 1. 목적과 용어

서비스 수준 지표(Service Level Indicator, SLI)는 기능의 정확성·지연·처리량·복구 상태를 측정하는 값이다. 서비스 수준 목표(Service Level Objective, SLO)는 정해진 조건과 기간에 SLI가 충족해야 하는 기준이다.

이 문서는 다음 세 종류의 값을 구분한다.

| 구분 | 의미 |
| --- | --- |
| 현재 기준선 | 기존 코드와 2026-09-19 재현에서 측정한 값 |
| 고정 SLO | 업무 정합성 때문에 구현 전에도 수치를 확정할 수 있는 목표 |
| 측정 후 확정 | 구현 뒤 동일 조건의 반복 측정으로 목표값을 정할 지표 |

운영 트래픽과 장기간 가용성 측정값은 아직 없다. Phase 2에서 MySQL 사건량·Writer 비용의 통제된 기준을 확보했고, Phase 3 조회 모델 처리 지연과 Phase 4 장애 지표는 추가 측정한다. 이 문서의 SLO는 Phase 2~5의 통제된 시험과 초기 운영 승인에 사용한다.

## 2. 측정 범위

### 2.1 생명주기 시작과 종료

- 시작: `ReservationCreated` 사건이 업무 상태와 함께 커밋된 시점
- 정상 종료: `ReservationCompleted`와 관련 사건이 커밋된 시점
- 만료 종료: `ReservationExpired`와 필요한 `PaymentRefundPending`이 커밋된 시점
- 조회 반영 완료: 연속된 `decisionVersion`까지 조회 모델에 적용된 시점
- 원천 일치 확인: 마지막 원천 대조가 `CONSISTENT`를 기록한 시점

### 2.2 집계 단위

| 지표 종류 | 기본 집계 단위 |
| --- | --- |
| 사건 정확성 | 사건 수와 `eventId` |
| 상태 정확성 | `lifecycleId` |
| 처리 지연 | 고유 사건과 생명주기 결정 단위 |
| 조회 성능 | `paymentOrderId`·`reservationId` 조회 요청 |
| 장애 복구 | 장애 주입 실행 1회 |
| 진단 효율 | 기준 질문을 조사하는 독립 실행 1회 |

시험 결과는 입력 데이터, 애플리케이션·MySQL 버전, 인스턴스 수, Poller 간격, 배치 크기와 실행 시각을 함께 보존한다.

## 4. SLI 정의

### 4.1 사건 생성 정확성

| SLI | 정의 |
| --- | --- |
| 커밋 사건 누락 수 | 기대한 커밋 업무 사건 중 `lifecycle_event`에 없는 고유 사건 수 |
| 롤백 사건 수 | 롤백된 업무 상태 변경에 대응해 남아 있는 사건 수 |
| 업무 사건 중복 수 | 하나의 상태 결정에 서로 다른 `eventId`로 중복 생성된 사건 수 |
| 사건 기록 추가 지연 | 사건 기록 전후 업무 API 또는 스케줄 작업 트랜잭션 시간 차이 |
| 잠금 유지 시간 변화 | 사건 기록 전후 같은 경합 시나리오의 Reservation 행 잠금 유지 시간 차이 |

### 4.2 처리 정확성

| SLI | 정의 또는 계산식 |
| --- | --- |
| 입력 사건 수 | Poller가 Consumer 처리 대상으로 읽은 사건 수, 재전달 포함 |
| 고유 사건 수 | 서로 다른 `eventId` 수 |
| 처리 사건 수 | 중복 제거 후 조회 모델에 적용한 고유 사건 수 |
| 중복 적용 수 | 같은 `eventId`가 상태에 두 번 이상 적용된 수 |
| 상태 일치율 | `CONSISTENT` 생명주기 수 ÷ 원천 대조한 생명주기 수 × 100 |
| 경로 판정 정확도 | 기대 경로와 일치한 기준 시나리오 수 ÷ 전체 기준 시나리오 수 × 100 |
| 순번 공백 수 | 원천 `lifecycleVersion`까지 연속되지 않은 `decisionVersion` 구간 수 |
| 재처리 결과 일치율 | 기존 결과와 상태·사건·경로가 모두 같은 생명주기 수 ÷ 재처리한 생명주기 수 × 100 |

### 4.3 처리 지연과 용량

| SLI | 정의 |
| --- | --- |
| 사건 가시화 지연 p50·p95·p99 | `lifecycle_event.recorded_at`부터 해당 결정의 적용 기록 `applied_at`까지의 시간 |
| 원천 일치 지연 p95 | 사건 커밋 시점부터 원천 대조 결과가 `CONSISTENT`가 되는 시점까지의 시간 |
| 최대 처리 대기량 | 실행 중 커밋됐으나 조회 모델에 적용되지 않은 고유 사건의 최대 수 |
| 처리율 | 단위 시간에 조회 모델에 적용한 고유 사건 수 |
| Poller 실행 시간 | 한 번의 Poller 실행 시작부터 처리 대상 확정까지의 시간 |
| Consumer 처리 시간 | 결정 단위 입력부터 적용 기록과 조회 모델 커밋까지의 시간 |
| 재처리 처리율 | 재처리에서 초당 적용한 고유 사건 수 |

초기 MySQL 폴링 구조는 행에 정확한 트랜잭션 커밋 시각을 저장하지 않는다. `recorded_at`은 사건 INSERT 시각이므로 위 지연에는 업무 트랜잭션의 남은 시간도 포함된다. 이 지표를 커밋 후 가시화 지연의 보수적인 대용값으로 사용하며, 순서 판정에는 사용하지 않는다.

### 4.4 복구성

| SLI | 정의 |
| --- | --- |
| 장애 복구 시간 | Consumer 재시작부터 장애 전 처리 대기량을 모두 해소하고 정상 지연 범위로 돌아올 때까지의 시간 |
| 재시작 후 누락 수 | 장애 주입 전후 기준 원천에 존재하며 최종 조회 결과에 반영되지 않은 사건 수 |
| 재시작 후 중복 적용 수 | 장애 주입 전후 같은 사건이 두 번 이상 상태에 적용된 수 |
| 미처리 생명주기 수 | 마지막 연속 버전까지 적용하지 못한 생명주기 수 |

### 4.5 조회와 진단 효율

| SLI | 정의 |
| --- | --- |
| 조회 성공률 | 유효한 식별자의 조회가 완전한 계약으로 반환된 비율 |
| 조회 지연 p50·p95·p99 | 조회 요청 수신부터 응답 완료까지의 시간 |
| 조회 결과 완전성 | 네 상태 축·사건·경로·신뢰 상태를 모두 포함한 응답 비율 |
| 추가 DB 조회·로그 검색 수 | 생명주기 조회 뒤 원인과 경로를 확인하기 위해 수행한 추가 작업 수 |
| 원인 확인 시간 | 식별자 입력부터 상태 원인을 근거와 함께 설명할 때까지의 시간 |

## 6. 성능·용량 기준

### 6.1 초기 검증 부하

운영 SLO를 확정하기 전 다음 부하를 기술 적합성 검증 경계로 사용한다.

| 부하 | 입력 조건 | 필수 판정 |
| --- | --- | --- |
| 지속 처리 | 500 events/s | 정확성 SLO 유지, 처리율·p95 지연·최대 처리 대기량 기록 |
| 만료 버스트 | 한 업무 트랜잭션에서 5,000개 만료 사건 생성 | 업무 트랜잭션 시간·잠금 유지 시간·처리 대기량 기록 |
| 재처리 | 보존 사건 30,000개 | 결과 일치율 100%, 처리율과 완료 시간 기록 |
| 중복 | 기준 사건 전체를 한 번 더 전달 | 중복 적용 0건, 추가 처리 비용 기록 |
| 순서 역전·지연 | 승인·만료 사건 순서 교환 및 일부 보류 | 최종 상태 일치율 100%, 지연 중 신뢰 상태 확인 |

500 events/s, 만료 사건 5,000개와 재처리 30,000개는 제품 운영 용량 약속으로 사용하지 않는다. MySQL 폴링 구조의 여유와 기술 재검토 필요성을 판단하는 시험 조건이다.

## 7. 측정 불변식

실행 결과는 다음 관계를 함께 확인한다.

```text
입력 사건 수 = 고유 사건 수 + 재전달된 중복 사건 수
고유 사건 수 = 처리 사건 수 + 미처리 사건 수
처리 사건 수 = 적용 기록의 고유 eventId 수
CONSISTENT 판정 = 조회 모델 버전과 원천 버전 일치
                  + 네 상태 축의 필드 값 일치
```

순번 공백으로 보류한 사건은 미처리 사건으로 집계한다. `PROCESSING`은 오류 수에 포함하지 않고 처리 대기량과 지연에 포함한다. 원천 대조로 사건 부재가 확인되면 `INCOMPLETE`로 집계한다.

## 8. 관측 지표 이름 제안

구현 시 Micrometer 이름은 프로젝트 명명 규칙에 맞게 확정한다. 다음 이름은 지표의 책임을 고정하기 위한 제안이다.

| 제안 이름 | 유형 | 의미 |
| --- | --- | --- |
| `lifecycle.events.committed` | Counter | 업무 트랜잭션과 함께 커밋한 사건 수 |
| `lifecycle.events.processed` | Counter | 조회 모델에 적용한 고유 사건 수 |
| `lifecycle.events.duplicate` | Counter | 재전달되어 적용하지 않은 사건 수 |
| `lifecycle.processing.lag` | Timer | 사건 가시화 지연 |
| `lifecycle.backlog` | Gauge | 현재 미처리 고유 사건 수 |
| `lifecycle.consumer.duration` | Timer | 결정 단위 Consumer 처리 시간 |
| `lifecycle.reconciliation.total` | Counter | 신뢰 상태별 원천 대조 결과 수 |
| `lifecycle.replay.duration` | Timer | 재처리 실행 시간 |
| `lifecycle.query.duration` | Timer | 생명주기 조회 응답 시간 |

`lifecycleId`, `reservationId`, `paymentOrderId`, `eventId`는 높은 카디널리티를 만들므로 메트릭 태그로 사용하지 않는다. 개별 건 근거는 보호된 조회와 구조화 로그에서 확인한다.

## 9. 단계별 품질 게이트

| Gate | Phase | 통과 조건 |
| --- | --- | --- |
| G0 | 0 | 현재 진단 기준선과 측정 절차 보존 |
| G1 | 1 | 요구사항, 기술 선택, C4, SLI·SLO와 품질속성 기준 승인 |
| G2 | 2 | SLO-C01~C03, SLO-R01 통과와 성능 기준선 확보 |
| G3 | 3 | SLO-C04~C06, SLO-C09 통과 |
| G4 | 4 | SLO-C07~C08 통과와 복구 시간 기준선 확보 |
| G5 | 5 | SLO-Q01~Q02 통과, 경로 판정 정확도 100%, 진단 기준선 재측정 |

목표값을 변경할 때는 원시 결과, 실행 조건, 변경 이유와 영향을 받는 요구사항 ID를 함께 기록한다. 기술 전환 조건은 [기술 선택 ADR](phase-1-technology-adr.md)의 8절을 따른다.
